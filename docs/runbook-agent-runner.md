# Runbook: автономный исполнитель (runner)

Документ для дежурного инженера. Описывает машину, на которой кодовый агент
работает под управлением `control-plane-agent`: запуск, остановку, отзыв
доступа и разбор частых отказов.

Runner — единственная часть системы, где агент пишет в файлы. Всё остальное
(claim, run, артефакты) он делает через тот же API, что и человек, поэтому
большинство сценариев из [operations.md](operations.md) применимо и здесь.

Адреса конкретного развёртывания — хост, ключ, идентификаторы Workspace — здесь
намеренно не приводятся: они принадлежат окружению, а не продукту. Держите их в
своих эксплуатационных заметках.

## Раскладка

```
<runner-root>/<repo>.git        bare-зеркало forge, источник рабочих копий
<runner-root>/<neighbour>.git   зеркало соседнего репозитория (path-зависимости)
<runner-root>/superproject.git  зеркало суперпроекта: его сабмодули задают ревизии соседей
<runner-root>/worktrees/<id>/<repo>/        рабочая копия на ветке task/<publicId>
<runner-root>/worktrees/<id>/<neighbour>/   сосед на ревизии из суперпроекта
<runner-root>/src/              клоны, из которых поставлен пакет
<runner-root>/claude/           runtime адаптера: mcp.json, логи сессий
<runner-root>/secrets/runner.env   конфигурация и токен подписки (0600)
~/.config/iam/credentials.json     PAT агента (0600)
```

Ключевые переменные:

| Переменная | Смысл |
|---|---|
| `CONTROL_PLANE_SERVER` | адрес Control Plane |
| `CONTROL_PLANE_IAM_URL`, `CONTROL_PLANE_IAM_TENANT` | где и от чьего имени менять PAT на access token |
| `CONTROL_PLANE_AGENT_WORKSPACE` | **очередь**, из которой берутся задачи |
| `CONTROL_PLANE_AGENT_REPO` | локальное bare-зеркало, источник рабочих копий |
| `CONTROL_PLANE_AGENT_WORKTREE_ROOT` | где живут рабочие копии |
| `CONTROL_PLANE_AGENT_BASE_REF` | от чего ветвиться при создании рабочей копии; по умолчанию `HEAD` |
| `CONTROL_PLANE_AGENT_PUSH_REMOTE` | remote для публикации веток; пусто — работа остаётся локальной |
| `CONTROL_PLANE_AGENT_PUBLISH_HOOK` | команда проверки цели перед каждым push (CP-ADR-0073, Е8); пусто — сверяются только адреса remote с конфигурацией (агент с каталогом предупреждает об этом при старте) |
| `CONTROL_PLANE_AGENT_RUNTIME_DIR` | куда скачиваются входы задач (`<dir>/<publicId>/inputs/<key>/<name>`, CP-ADR-0072 §8); по умолчанию `<WORKTREE_ROOT>/.runtime` |
| `IAM_PRINCIPAL` | какой Principal этой машины обслуживает процесс; обязателен, когда исполнителей несколько |
| `CONTROL_PLANE_AGENT_NEIGHBOURS` | соседние репозитории для сборки: `platform-auth-sdk=<runner-root>/platform-auth-sdk.git` |
| `CONTROL_PLANE_AGENT_SUPERPROJECT` | зеркало суперпроекта, чьи сабмодули закрепляют ревизии соседей |
| `CLAUDE_CODE_OAUTH_TOKEN` | токен подписки; принадлежит человеку, не агенту |

Не путайте `CONTROL_PLANE_AGENT_WORKSPACE` (Workspace в Control Plane) и
`CONTROL_PLANE_AGENT_WORKTREE_ROOT` (каталог рабочих копий) — это разные вещи с
похожими именами.

Без `CONTROL_PLANE_AGENT_NEIGHBOURS` рабочая копия `control-plane` **не
собирается**: `platform-auth-sdk` подключён path-зависимостью `../platform-auth-sdk`
и должен лежать соседней папкой. Подробности и полный список переменных —
[execution-workspace.md](execution-workspace.md).

## Управление

```bash
systemctl status control-plane-runner
systemctl stop control-plane-runner
journalctl -u control-plane-runner -n 50
```

Остановка безопасна в любой момент. Агент получает `SIGTERM`, текущий turn
прерывается, незавершённый run остаётся `running` до истечения аренды. При
следующем старте агент читает `/harness/context`, находит свой осиротевший run
и честно валит его с `failure_reason=restart_recovery` — задача возвращается в
очередь, а не зависает. Ждать «чистого момента» не нужно.

Рабочая копия при этом сохраняется: следующая попытка той же задачи
переиспользует её вместе с незакоммиченными изменениями.

## Отмена и сторож прогресса

Пока исполнитель (Claude Code, Codex, OpenCode) работает, демон читает свой
run не реже раза в 30 секунд:

- **Запрос отмены** (`POST /runs/{id}:request-cancel` — человек или правило,
  чья предпосылка исчезла, ADR-0063 амендмент А4) — демон останавливает
  исполнителя (процесс CLI убивается, сессии OpenCode посылается abort),
  подтверждает control message (`applied`), завершает run как `cancelled` с
  причиной `cancel_requested` и освобождает claim. Решение правила о задаче
  применяется после этого, на следующем проходе worker'а.
- **Нет прогресса** — run не записал ни одного действия
  `CONTROL_PLANE_AGENT_STALL_WARN_SECONDS` (600) секунд: checkpoint `stall` с
  последним действием. После `CONTROL_PLANE_AGENT_STALL_STOP_SECONDS` (1800)
  исполнитель останавливается, run завершается `failed` с причиной
  `no_progress`, claim освобождается — задача возвращается в очередь.
- **Действие ещё идёт** — если последнее действие run в статусе `started`
  (не завершено: например, идёт полный прогон тестов), оно считается живым.
  Checkpoint `stall` пишется по прежнему порогу, но с `actionRunning: true` и
  пометкой `note` «action still running: <action> since <startedAt>»; остановка
  `no_progress` — только после `CONTROL_PLANE_AGENT_ACTION_MAX_SECONDS` (3600,
  не меньше порога остановки). Завершение такого действия считается прогрессом.

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `CONTROL_PLANE_AGENT_CONTROL_POLL_SECONDS` | 15 | как часто читать run (не больше 30) |
| `CONTROL_PLANE_AGENT_STALL_WARN_SECONDS` | 600 | тишина до checkpoint `stall`; 0 — выключено |
| `CONTROL_PLANE_AGENT_STALL_STOP_SECONDS` | 1800 | тишина до остановки `no_progress`; 0 — выключено |
| `CONTROL_PLANE_AGENT_ACTION_MAX_SECONDS` | 3600 | предел для незавершённого последнего действия (не меньше `STALL_STOP`) |
| `CONTROL_PLANE_AGENT_RETRY_WINDOW` | 300 | сколько секунд повторять чтения и команды с ключом идемпотентности, пока ядро недоступно (502/503/504, сетевой сбой); дольше — прогон проваливается; не число или отрицательное — демон не стартует (код 2) |

Heartbeat аренды сессии и claim терпит недоступность ядра 180 s с последнего
успешного heartbeat (три интервала по 60 s), повторяя его каждые 10 s; дольше —
аренда считается потерянной (`lease_lost`).

Сторож смотрит только на поток действий run: одно действие на каждый вызов
инструмента пишет адаптер (`started`, по результату — `completed`/`failed`),
остальные — агент через MCP. Поэтому долгий вызов инструмента живёт до
`ACTION_MAX`, а долгий шаг вовсе без действий — только до порога остановки.
Смотрится только последнее действие: если после долгого вызова записано и
завершено другое (параллельные вызовы), действует обычный порог.

## Ревью работы агента

Когда задан `CONTROL_PLANE_AGENT_PUSH_REMOTE`, демон после коммита публикует
ветку `task/<publicId>` — и ревью идёт там же, где ревью людей.

Публикует именно демон, а не агент внутри: claim и его fencing token держит
процесс-демон, поэтому опубликованное им атрибутируется тому run, который это
произвёл. По той же причине агент не решает свой исход.

Три ограничения публикации, о которых стоит знать:

* пушится только ветка задачи и никогда базовая — runner предлагает работу к
  рассмотрению, а не двигает линию, на которой строят остальные;
* push никогда не форсируется: разошедшаяся ветка в forge — это то, что
  разбирает человек, а перезапись уничтожила бы ровно ту историю ревью, ради
  которой всё и делается;
* неудача публикации не валит run. Коммит уже является evidence, и
  недоступный forge не должен превращать сделанную работу в проваленную.
  Ветка попадает в `<WORKTREE_ROOT>/.unpublished.json` и отправляется снова в
  следующем цикле демона, дальше — с растущей паузой до 30 минут; ветка,
  которую в forge переписали (не fast-forward), снимается с предупреждением.
  Повтор не вечен: после 12 неудач подряд или через 6 часов после первой
  ветка снимается из списка, в журнале — warning `not published after N
  attempt(s), giving up`, в задаче — комментарий «The branch … was not
  published after N attempt(s): <причина>». Это сигнал человеку: forge
  стабильно отказывает (отозван токен, защита ветки, pre-receive). Исправьте
  причину и верните задачу — следующая сдача опубликует ветку заново; коммит
  всё это время лежит в зеркале runner. Так же идёт и временный отказ хука
  публикации (`CONTROL_PLANE_AGENT_PUBLISH_HOOK`): код выхода `75`
  (`EX_TEMPFAIL` — forge ответил 5xx, сбой сети) значит «проверить сейчас
  нельзя», ветка попадает в тот же список и повторяется с тем же пределом.
  Отказ проверки цели (`publish_target_rejected`: адрес не из каталога или
  любой другой ненулевой код хука) — другое дело: ничего не отправлено, задача
  ждёт человека в `blocked`.

Список неопубликованного держит и диск. Что знать дежурному:

* **Диск растёт, пока forge недоступен.** Копии задач из
  `.unpublished.json` лимит `CONTROL_PLANE_AGENT_MAX_WORKSPACES` не вытесняет
  и не считает (CP-ADR-0073, Е8): вытесненная копия молча сняла бы ветку с
  повтора. Поэтому при долгом сбое forge копий на диске больше лимита — каждая
  сданная, но не опубликованная задача добавляет свою, — пока их записи не
  исчерпают повторы (12 неудач подряд или 6 ч с первой) и не снимутся; дальше
  копии снова вытесняются как обычные. Это осознанно: потерять
  неопубликованную работу хуже, чем временно превысить лимит. Что мониторить:
  свободное место тома `CONTROL_PLANE_AGENT_WORKTREE_ROOT`, число записей в
  `.unpublished.json` (`items`) и warning `push of … failed` и `not published
  after N attempt(s), giving up` в журнале. Если места не хватает раньше, чем
  forge вернулся, — освободите том или остановите демон; удалять копии из
  списка руками не нужно, их ветки ещё не в forge.
* **Битый `.unpublished.json` останавливает вытеснение.** Файл, который есть,
  но не разбирается (битый JSON, нет `items`), — это «какие копии ждут,
  неизвестно», поэтому лимит не вытесняет ни одной копии, а в журнале при
  каждой попытке вытеснения — warning `the unpublished list cannot be parsed;
  no copy pruned`. Отсутствующий файл значит «ничего не ждёт». Что делать:
  сохраните файл для разбора, по возможности восстановите записи (формат —
  `{"items": [...]}`, поля записи — в `publish.py`, `Unpublished.as_json`)
  или удалите файл, если повторять нечего; вытеснение возобновится со
  следующей попыткой.
* **Новая запись поверх битого файла.** Следующий сбой push пишет файл заново
  — уже с одной своей записью; записи, которые были в битом файле, теряются.
  Их копии перестают быть закреплёнными и снова могут быть вытеснены, а ветки
  больше не повторяются. Коммиты при этом не пропадают: ветки остаются в
  зеркале runner (вытеснение удаляет рабочую копию, но не ветку). Чтобы
  опубликовать такую ветку, найдите задачи по warning `push of … failed` в
  журнале до перезаписи и верните их —
  следующая сдача опубликует ветку из зеркала.

Поэтому у артефакта типа `commit` есть поле `published`. Если оно `false` —
ветки в forge нет, коммит существует только на runner, и ревьюеру там смотреть
нечего. Полный вывод git остаётся в логе runner: в нём бывают адрес remote и
локальные пути. Наружу — в комментарий об исчерпании повторов — уходит одна
строка причины без учётных данных в адресах и без локальных путей.

## Что ограничивает потребление

Задаётся в юните, потому что Node с кодовым агентом внутри способен занять всю
машину:

| Параметр | Зачем |
|---|---|
| `CPUQuota` | оставить процессорное время соседям |
| `MemoryHigh` / `MemoryMax` | потолок на весь cgroup, включая дочерний процесс агента |
| `IOWeight` | git-операции не должны конкурировать с базами за диск |
| `CONTROL_PLANE_AGENT_MAX_WORKSPACES` | сколько простаивающих рабочих копий держать; копии с неопубликованной веткой не считаются и не вытесняются — при сбое forge диск растёт сверх лимита (см. «Ревью работы агента») |

## Режим агента

Principal, привязанный к агенту реестра (CP-ADR-0073), настраивается не
переменными, а ревизией своего агента (`GET /agents/me`, п.14 ADR):
отбор работы, исполнитель и его параметры, инструкции, рабочая копия и
соседи, ревью, скиллы, `drainSeconds`. Переменные хоста (адрес, credential,
`CONTROL_PLANE_AGENT_WORKTREE_ROOT`, `CONTROL_PLANE_AGENT_MIRRORS`, бинарники,
логи) действуют как раньше. `CONTROL_PLANE_AGENT_CONFIG=env` принудительно
включает env-режим (только для principal без агента), `revision` — требует
агента.

Коды выхода: `75` — появилась новая ревизия (или её не удалось прочесть при
старте), перезапустить; `0` — агент остановлен или выведен из оборота; `2` —
конфигурация неисполнима (вид исполнителя, параметры, зеркало чужого
репозитория), в журнале — причина.

`SIGTERM` в обоих режимах: новых задач демон не берёт, текущий прогон
получает `drainSeconds` (в env-режиме — `CONTROL_PLANE_AGENT_DRAIN_SECONDS`;
без неё прогон доводится до конца), потом отменяется `drained` и задача
возвращается в очередь.

## Какие задачи он берёт

Агент берёт **первую доступную задачу по приоритету**, а не назначенную ему.
Единственный ограничитель — `CONTROL_PLANE_AGENT_WORKSPACE`.

Убрать эту переменную — значит выпустить агента в общую очередь, где лежат
эпики и задачи, к которым его репозиторий может не иметь отношения. Делать это
следует сознательно и не раньше, чем появится штатная деградация (approval
gate, бюджет, отмена).

## Отзыв доступа

Два независимых доступа, отзываются отдельно.

**PAT агента** (Control Plane). Отзыв — в IAM; после него агент не получает
access token и не может ни claim, ни писать. Уже выданный токен живёт до
истечения. Отрицательный ответ кэша отзыва не переспрашивается до конца жизни
процесса, поэтому `control-plane-api` начнёт отказывать сразу, как увидит
отзыв, и обратно не пустит без перезапуска. Локальный Principal остаётся:
история работы не теряется.

**Токен подписки** — принадлежит человеку, а не агенту, и отзывается на стороне
поставщика. После отзыва агент продолжит брать задачи и валить их, поэтому
сервис надо остановить.

Обрубить всё, не разбираясь:

```bash
systemctl stop control-plane-runner && systemctl disable control-plane-runner
```

## Тестовые сервисы прогона

Сервисы, которые объявляет `services` в `.agents/runner.yaml` базовой ревизии
задачи, демон запрашивает у слушателя `fleet-services` своего узла перед
исполнителем и передаёт адрес и учётку только в окружение этого прогона
(`control_plane_agent/services.py`, CP-ADR-0073 Е6; формат —
[runner_config.md](../src/control_plane_agent/runner_config.md)).

| Переменная | Смысл |
|---|---|
| `FLEET_SERVICES_URL`, `FLEET_SERVICES_TOKEN_FILE` | адрес слушателя и файл токена контейнера; узел задаёт их только виду исполнителя с `services: true`, всегда парой |
| `FLEET_REPLICA` | номер реплики (0–99); задаёт узел |
| `CONTROL_PLANE_AGENT_KEY` | ключ агента в env-режиме; в режиме агента — ключ ревизии |
| `CONTROL_PLANE_AGENT_SERVICES` | `fleet` (по умолчанию) — спрашивать узел; `host` — ничего не спрашивать, исполнитель живёт тем, что дал хост (статические базы до этапа 2) |

Одна переменная пары без другой, пара без `FLEET_REPLICA` или без ключа
агента, неизвестный режим — выход 2 при старте.

| Причина провала прогона | Что с задачей | Что делать |
|---|---|---|
| `test_services_unavailable` | в очередь, claim снят | бюджет памяти сервисов узла занят или сервис не поднялся за `waitSeconds` (600 с): задача вернётся сама; повторяется — смотреть узел |
| `service_template_unavailable` | `blocked` | в `node.yaml` узла нет шаблона из `runner.yaml`: завести шаблон или поправить `runner.yaml` на базовой ветке |
| `service_quota_exceeded` | `blocked` | сервисов больше `perReplica` узла |
| `test_services_not_offered` | `blocked` | `runner.yaml` объявляет сервисы, а у раннера нет слушателя, файл токена не читается, исполнитель не принимает окружение прогона или задачу взяла обвязка `control-plane-opencode`, которая сервисы не запрашивает |
| `test_services_refused` | `blocked` | слушатель отверг токен, пару «агент, реплика» или запрос, либо ответил вне контракта |
| `runner_config_invalid` | `blocked` | `runner.yaml` базовой ревизии не проходит разбор; ошибки — в комментарии |

Ожидание сервисов прерывается отменой прогона и концом drain, как работа
исполнителя: прогон отменяется `cancel_requested` или `drained`, запрос у
узла отзывается. Claim, потерянный за ожидание, — `lease_lost`, исполнитель
не запускается.

## Частые отказы

**`control-plane-agent has no credentials for ...`** — не найден ни PAT, ни
API-ключ. Проверить `~/.config/iam/credentials.json` (режим обязан быть `600`,
иначе клиент откажется читать) и переменные IAM.

**`iam_environment_mode_required`** — `IAM_PLATFORM_ACCESS_TOKEN` задан без
`IAM_CREDENTIAL_MODE=environment`. Защита: унаследованная переменная не должна
молча подменять учётную запись. Файловому пути этого не требуется.

**`iam_credential_ambiguous`** — на машине несколько credential одного тенанта
(например runner и ревьюер), а процесс не сказал, кто он. Задать `IAM_PRINCIPAL`
в его юните. Разводить `XDG_CONFIG_HOME` для этого больше не нужно: записи
различаются по Principal и живут в одном файле. Отказ здесь намеренный —
выбрать одну из записей наугад значило бы работать под чужой identity, а
заметно это стало бы только в audit.

**`binding_not_found`, и после починки не проходит** — отрицательный ответ кэша
отзыва не переспрашивается. Перезапустить `control-plane-api`.

**Задача взята, но ничего не происходит** — проверить, жив ли процесс агента.
Turn ограничен `CONTROL_PLANE_CLAUDE_TIMEOUT` (по умолчанию час): зависший
процесс не держит лизу вечно, но и не отпустит её быстро.

**`workspace ... is held by another process`** — рабочая копия занята другим
процессом. Сейчас это честный отказ run с `failure_reason=workspace_busy`.

**`could not read Username for 'https://...'` при публикации ветки** — процессу
не задан `HOME`, поэтому git не нашёл `~/.gitconfig`, а с ним и credential
helper. systemd не выставляет `HOME` сам, даже сервисам от root: нужен явный
`Environment=HOME=...` в юните. Симптом обманчив — выглядит как проблема с
правами в forge, а на деле до forge дело не дошло. Признак, что вы попали
именно сюда: run завершается успешно, а в артефакте `commit` стоит
`published: false`.

**Кончилась память** — `MemoryMax` убьёт процесс, systemd перезапустит, run
будет закрыт как `restart_recovery`. Если повторяется, задача слишком тяжела
для этой машины: её надо делать в другом месте, а не поднимать потолок.

## Обновление кода runner

```bash
cd <runner-root>/src/<repo> && git pull
uv tool install --reinstall .
cd <runner-root>/<repo>.git && git fetch origin '+refs/heads/main:refs/heads/main'
systemctl restart control-plane-runner
```

Обновлять надо оба места: `src/` — то, из чего собран сам агент, зеркало — то,
из чего он делает рабочие копии для задач. Забыть второе легко, и тогда агент
будет чинить код, которого уже нет.

## Что runner намеренно не делает

- **не открывает pull request и не вливает ветку** — публикация ветки это
  предложение к рассмотрению, решение принимает человек;
- **не решает свой исход** — `succeed`/`fail`/`suspend` вызывает демон,
  держащий claim и его fencing token, а не агент внутри;
- **не отправляет наружу промпты и рассуждения** — они остаются в локальном
  логе; в Control Plane уходят summary, счётчики и ограниченный
  отредактированный транскрипт хода (сообщения, вызовы инструментов, итог) —
  ADR-0051; `CONTROL_PLANE_TRACE_*` сужает это на конкретной площадке.
