# ADR-0066: Инструкции исполнителю у типа задачи — слои, общий рендер, хэш на run

Статус: Accepted (2026-09-25). Частичная реализация TAI-ADR-0009 (слои инструкций
Worker Profile: слой проекта и слой задачи). Основание — TAI-ADR-0047 п.5 (цикл
spec-driven разработки: инструкции шага приходят исполнителю из типа задачи).

Контекст: ADR-0048 (реестр типов задач), ADR-0061 (исходы approval объявляет тип),
ADR-0059/ADR-0064 (пакет контекста — данные, а не инструкции), ADR-0056 (скиллы).

## Контекст

Исполнитель (раннер или харнесс человека) получает сейчас: описание задачи, пакет
контекста памяти и, только в адаптере Claude Code, один файл соглашений на хосте
раннера (`CONTROL_PLANE_CLAUDE_PROMPT_FILE`). Адаптеры Codex и OpenCode вместо него
вставляют сырой JSON `effectiveConfig` проекта. У типа задачи нет места для «как
выполнять задачу этого типа», поэтому такие указания дублируются в каждом
описании задачи (шаблоны `ensureWork`) или зашиваются в код демона
(`control_plane_agent/review.py`). Слои инструкций TAI-ADR-0009 не реализованы:
ни хранения, ни версии, ни следа в run.

## Решение

1. **Поле `instructions` у версии типа задачи** (`task_types.instructions`, текст
   Markdown до 16 KiB, пустое по умолчанию). Иммутабельно в версии, как
   `approval_schema` и `context_schema`: изменение инструкций — новая версия
   типа. Проверяется при публикации: размер, отказ от секретов
   (`reject_secret_material`). В API — `instructions` в запросе и ответе версии
   типа; в пакете каталога — поле `spec.instructions` вида `TaskType`.

2. **Слой проекта** — `settings.agentInstructions` в конфигурации проекта
   (эффективная конфигурация с наследованием, ADR о конфигурации проекта):
   принципы и соглашения всего проекта. Для цикла TAI-ADR-0047 туда ставится
   конституция или ссылка на неё.

3. **Порядок слоёв** в собранных инструкциях — от общего к частному, каждый слой
   под своим заголовком и с источником:
   1. контракт платформы (фиксированный текст ядра: протокол claim/run, отчёт,
      границы полномочий) — первым, нижние слои его не отменяют;
   2. проект (`settings.agentInstructions`);
   3. тип задачи (`instructions` версии типа);
   4. репозиторий — файл соглашений исполнителя (`CONTROL_PLANE_CLAUDE_PROMPT_FILE`
      и его аналоги для других адаптеров) — добавляет сам исполнитель, ядро его
      не знает.

   Слои дописываются, а не сливаются: ядро не пытается разрешать противоречия в
   прозе. Противоречие слоёв — ошибка содержания, её видно в аудите по хэшу и
   источникам.

4. **Доставка.** `GET /runs/{run_id}/context` (и MCP `cp_get_run_context`)
   возвращает блок `instructions: {layers: [{source, ref, version, text}], hash}` —
   слои 1–3, собранные ядром; хэш — sha256 канонического текста слоёв 1–3. Этот же
   блок получает харнесс человека (TAI-ADR-0047: шаги дизайна исполняет харнесс
   владельца), не только раннеры.

5. **Общий рендер** — `control_plane_agent/instructions.py`: одна функция
   собирает текст prompt из блока `instructions` и файла соглашений репозитория
   для всех адаптеров (Claude Code, Codex, OpenCode). Сырой JSON `effectiveConfig` в
   prompt больше не вставляется; пакет контекста памяти остаётся отдельно и
   по-прежнему помечен как данные, а не инструкции (ADR-0059).

6. **След на run.** При старте run хэш инструкций и ссылки на версии слоёв
   (`taskTypeVersion`, ревизия конфигурации проекта) записываются в run
   (`instructions_hash` и `instructions_refs` или метаданные run — на выбор
   реализации, без изменения смысла) и в событие `run.started`. По хэшу видно, с
   какими инструкциями выполнялась работа.

## Границы

- Worker Profile, слои tenant, позиции/роли и principal, выкатка ревизий профиля —
  по TAI-ADR-0009, позже.
- Ядро не исполняет инструкции и не проверяет их соблюдение: соблюдение
  проверяется воротами (approval, скиллы-проверки), не текстом.
- Файл соглашений репозитория остаётся на стороне исполнителя.

## Последствия

- Инструкции шагов цикла TAI-ADR-0047 живут в типах задач пакета `sdd` и
  версионируются вместе с ними.
- Адаптеры собирают prompt одинаково; Codex впервые получает соглашения.
- Шаблоны описаний задач (`ensureWork`) сокращаются до сути задачи.

## Реализация (TASK-000373)

- Хранение: `task_types.instructions` (text, `''` по умолчанию, в триггере
  иммутабельности версии), `runs.instructions_hash` и `runs.instructions_refs`
  (`{hash, layers: [{source, ref, version}]}`) — колонки, а не метаданные run:
  метаданные пишет клиент при старте. Миграция `ffbbd22726d3`.
- Проверка секретов: текст инструкций — проза без ключей, поэтому
  ключевая `reject_secret_material` к нему неприменима; проверяется материал
  секрета в тексте (`secret_material` из `domain/redaction.py`, как у
  комментариев и evidence), код ошибки тот же — `secret_material_rejected`.
  Для типа — при публикации версии, для проекта — в `validate_config_document`
  (ревизии, настройки профиля, умолчания шаблона).
- Слои: `platform` (`control-plane:platform-contract`, версия текста ядра —
  `PLATFORM_CONTRACT_VERSION`, при правке текста увеличивается), `project`
  (`project:<id>`, версия — номер активной ревизии конфигурации проекта задачи;
  проект — ближайший предок workspace задачи с профилем), `taskType`
  (`taskType:<key>`, версия типа). Хэш — `sha256:` от канонического JSON слоёв
  (ключи отсортированы, строки NFC, UTF-8, без пробелов); общий
  `domain/canonical.py` не подходит из-за лимита длины строки.
- Доставка: `GET /runs/{id}/context` (слои как они стоят сейчас; запись в run —
  с чем run начинался), `POST /context` при фокусе на задаче или run — этим
  путём блок получают адаптеры при старте работы; OpenCode теперь передаёт
  `runId`. Слой проекта отдаётся без `projects:read`: это проза для исполнителя
  задачи, не конфигурация проекта.
- Рендер: протокол, отчёт и границы полномочий из заметок адаптеров перенесены
  в контракт платформы; в адаптерах осталась заметка о среде харнесса (доступен
  ли MCP, где работать, что записывается). Файлы соглашений:
  `CONTROL_PLANE_CLAUDE_PROMPT_FILE`, `CONTROL_PLANE_CODEX_PROMPT_FILE`,
  `CONTROL_PLANE_OPENCODE_PROMPT_FILE`.
