# ADR-0058: Неизвестный query-параметр — 400, а не тихо проигнорированный фильтр

Статус: Accepted (TASK-000062, 2026-09-23)

Контекст: инцидент 2026-08-14, зафиксированный в платформенном ADR-0018 как
решение 6; ADR-0010 — eligibility и `/work/available`; единый конверт ошибок
(`docs/api.md`, «Формат ошибок»).

## Контекст

Исполнителю добавили серверный фильтр очереди `assignedToMe`, клиент обновили,
а релиз сервера на стенд не выкатили. FastAPI по умолчанию отбрасывает
query-параметры, которых нет в сигнатуре endpoint'а, поэтому
`GET /work/available?assignedToMe=true` вернул полную очередь. Агент заклеймил
боевой эпик TASK-000002 и начал работать над ним в чужом репозитории. Заметили
через полторы минуты, ущерба нет.

Отказ был бесшумным и выглядел как успех: клиент считал, что фильтрует, сервер
считал запрос корректным. Клиентская проверка тут не помогает — сервер вправе
тихо не выполнить её условие. То же относится к будущим ограничителям: бюджету
(AR-5) и праву делегировать (AG-6). Тело запроса уже валидируется строго
(лишнее поле → `400 invalid_request`); query-строка — нет.

## Решение

Строгий режим для query-строки **на всём `/api/v1`** (вариант 1 задачи, без
списка исключений).

1. Router-level зависимость `reject_unknown_query_params`
   (`control_plane.api.strict_query`) сравнивает имена параметров запроса с
   объявленными у сработавшего route, включая параметры его зависимостей.
   Допустимое множество выводится из сигнатуры, поэтому новый `Query(...)`
   разрешается сам, без отдельной регистрации.
2. Неизвестный параметр → `400 invalid_request`, тот же конверт, что у
   нарушения контракта в теле. Каждый непонятый параметр назван в
   `error.details.errors[].loc` как `query.<имя>`; текст `message` контрактом
   не является.
3. Проверка выполняется до аутентификации и до обращения к БД: запрос с
   непонятым фильтром не доходит до выборки вообще.
4. WebSocket `GET /events/ws` не затронут: он отвечает кодами закрытия, а не
   конвертом ошибки, и его единственный параметр — курсор, не сужающий выдачу.
   Эндпоинты вне `/api/v1` (`/health/*`, `/metrics`) параметров не принимают и
   тоже не затронуты.

### Почему не список «ограничивающих» параметров (вариант 2)

Вариант 2 мягче к старым клиентам, но переносит защиту в список, который
поддерживают руками. Инцидент случился именно с **новым** параметром: в таком
списке его пришлось бы не забыть добавить — ровно та ошибка, от которой
защищаемся. Кроме того, «ограничивающий» — почти каждый query-параметр API
(фильтры, `limit`, `cursor`, `sort`); список совпал бы со всеми параметрами
list-endpoint'ов, только с риском отстать.

Цена строгости для совместимости невелика:

- **новый клиент → старый сервер** (случай инцидента) — теперь `400` вместо
  тихой полной выдачи; это и есть цель;
- **старый клиент → новый сервер** ломается, только если сервер *убрал*
  параметр; это и так изменение контракта, и молчаливое игнорирование в этом
  случае так же опасно;
- собственные клиенты платформы (`control_plane_client`, MCP-сервер, runner)
  шлют только объявленные параметры — полный набор тестов проходит без
  изменений в них.

## Последствия

- Авторы клиентов могут опираться на правило: `2xx` означает, что сервер понял
  **все** переданные query-параметры. Опечатка или параметр, до которого сервер
  ещё не обновлён, дают `400` с именем параметра.
- Защита работает только на сервере, где это изменение развёрнуто. Сервер
  старее этой версии по-прежнему молча игнорирует неизвестное.
- Добавлять служебные параметры «на всякий случай» (cache-buster вроде `_=`)
  нельзя: они тоже будут отклонены. Нужен такой параметр — объявите его в
  route.
- Консоль platform-web запрашивает `GET /runs/{id}/checkpoints` с `limit`, а
  этот маршрут, как и `GET /runs/{id}/actions`, параметров не объявлял и отдавал
  весь журнал одной страницей. Строгий режим превратил бы это в `400`,
  поэтому оба маршрута получили `limit`/`cursor` (курсор — по `seq`, max 200).
  Пагинация у них только по запросу: без `limit` и `cursor` журнал отдаётся
  целиком, как раньше (TASK-000284). Экран прогона в консоли читает actions
  без курсора (на staging — до 348 записей), а адаптеры исполнителей ищут
  последний checkpoint с хвоста списка; обрезка до default-страницы в 50
  записей молча сломала бы и то и другое. При явном `limit` и/или `cursor` —
  обычная страница (без `limit` — 50) с `nextCursor`. Прочие списки без
  query-параметров (`/tasks/{ref}/relations`, `/runs/{id}/harness-manifests`,
  `/principals/{id}/roles|capabilities|skills|iam-bindings`) возвращают
  ограниченный набор одной сущности и пагинации не получили: `limit` на них —
  `400`.
- Тесты: `tests/integration/test_discovery_v03.py` —
  `test_misspelled_narrowing_parameter_does_not_return_the_whole_queue`
  (опечатка в `assignedToMe` не отдаёт очередь, ошибка указывает на параметр) и
  `test_unknown_parameter_is_refused_on_every_listing_not_only_the_queue`;
  `tests/integration/test_execution_v03.py` —
  `test_run_log_accepts_limit_and_pages_by_cursor` и
  `test_run_log_without_limit_returns_every_entry`.
