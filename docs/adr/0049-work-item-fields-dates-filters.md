# ADR-0049: Custom fields, плановые даты и расширенная выборка work item

Статус: Accepted (v0.8, TASK-000027)

Контекст: ADR-0015 «Модель work item» верхнего уровня, «Решение» п.3, 4, 7;
прецедент — ADR-0031 (`custom_fields` и плановые даты Project Profile) и
ADR-0048 (реестр типов, чей `field_schema` до сих пор ни к чему не применялся).

## Контекст

ADR-0048 завёл `task_types.field_schema` пустой колонкой и явно оставил её
неприменённой: тип уже описывал словарь статусов, но не описывал поля. У задачи
не было ни расширяемых полей, ни плановых дат — только `created_at`,
`updated_at` и `completed_at`. Проектные атрибуты (компонент, blast radius,
severity) уезжали в текст описания, а отчётность по срокам построить было не из
чего.

Выборка `GET /tasks` фильтровала по статусу, категории, типу, приоритету,
assignee, workspace и project. Owner и даты не фильтровались, порядок был один —
`(created_at, id)` по убыванию. «Что горит на этой неделе» на таком контракте не
формулируется.

## Решение

1. **`tasks.custom_fields` (JSONB)** — валидируется при записи против
   `field_schema` **того типа и той версии, которые задача закрепила**, а не
   новейшей. Пустая схема принимает всё, поэтому задачи, созданные до этого
   решения, и системный тип продолжают работать без изменений.

2. **Тот же набор guard'ов, что у конфигурации проекта**: `guard_json_document`
   (размер, глубина, число узлов) до того, как документ увидит движок схем;
   запрет внешних `$ref` — стороннюю схему никто не резолвит и сетевых
   обращений не делает; `reject_secret_material` поверх. Секретный скан на
   custom fields — отличие от Project Profile, где он покрывает только
   `settings`: задачу правят агенты, и это более вероятное место для случайно
   вставленного токена.

3. **Замена целиком, а не merge.** Частичный документ нельзя проверить схемой с
   `required`, а merge не позволяет удалить ключ. Явный `null` отклоняется
   (`invalid_field`): очистка — это `{}`.

4. **`start_date` и `due_date` — типизированные колонки** `timestamptz`, а не
   ключи внутри документа: по ним нужны индексы, сортировка и timeline. Naive
   datetime читается как UTC. Обратный интервал отклоняется приложением
   (`invalid_planned_dates`) и `CHECK ck_tasks_planned_dates_ordered` в БД;
   частичное обновление сверяется с **сохранённым** вторым концом.

5. **Фильтры** `ownerId`, `startFrom`, `startTo`, `dueFrom`, `dueTo`. Границы
   дат включающие; ограничение по дате само по себе исключает задачи без неё —
   NULL не удовлетворяет сравнению.

6. **Порядок `sort=dueDate|startDate`** — ближайшие первыми, задачи без даты в
   хвосте, тай-брейк по `id`. Порядок **тотальный**: у команды с общим сроком
   даты равны, и без тай-брейка страницы теряли бы и дублировали строки. Курсор
   даты имеет собственный ключ (`d`), поэтому курсор, выданный под другим
   порядком, отклоняется как `invalid_cursor`, а не пагинирует молча неверно.

7. **События несут факт, а не содержимое.** В `task.created` попадают даты и
   булев `customFields`, в `task.updated` — `changes.custom_fields: true`.
   Журнал читают шире, чем саму задачу.

## Границы

Фильтрации по значению внутри `custom_fields` нет: это требует индексируемой
схемы запроса и решается отдельно. Классификация по областям и компонентам
выражается деревом Workspace и custom fields — отдельной сущности меток не
вводится (ADR-0015, «Границы»).

Вне объёма: метки, ранжирование для kanban, полнотекстовый поиск, watchers,
отображение полей и дат в web-интерфейсе.

## Не принято

- **Хранить даты внутри `custom_fields`.** Индекс по выражению из JSONB и
  сортировка по нему — это те же колонки, только без типов и без CHECK.
- **Merge-семантика для `custom_fields`.** См. п.3.
- **Сортировка по дате с исключением задач без неё.** Тихо терять строки из
  выборки хуже, чем показать их в хвосте; отсечь их — работа фильтра.
- **Один курсор на все порядки.** Курсор, применённый к другому `sort`,
  давал бы правдоподобные, но неверные страницы.
- **Валидация custom fields против новейшей версии типа.** Задача закрепляет
  версию; проверка по новейшей ломала бы записи, легальные при создании.

## Последствия

- `field_schema` из ADR-0048 наконец что-то значит: тип описывает и статусы, и
  поля, а значит вопрос, операция и инцидент получают свои атрибуты в ядре, а не
  в тексте.
- Появляется второй порядок чтения задач и второй формат курсора — цена в том,
  что клиент обязан передавать курсор вместе с тем же `sort`.
- Три дополнительных индекса на `tasks`; два из них частичные, потому что
  большинство задач дат не несёт.

## Минимальные критерии проверки

- `custom_fields`, не проходящие `field_schema` типа, отклоняются; внешний
  `$ref` не резолвится и не порождает сетевого обращения; секрет отклоняется;
- документ сверх лимита размера/глубины отклоняется до валидации схемой;
- обратный интервал отклоняется и при создании, и при обновлении одного конца,
  и на уровне БД; отклонённое обновление не меняет версию задачи;
- фильтры применяются до пагинации; страницы под `sort=dueDate` покрывают
  выборку ровно один раз при равных датах;
- отсутствие `due_date` не влияет на выборку по умолчанию;
- курсор чужого порядка → `invalid_cursor`, неизвестный `sort` → `invalid_sort`;
- ни фильтры, ни сортировка не пересекают границу тенанта.
