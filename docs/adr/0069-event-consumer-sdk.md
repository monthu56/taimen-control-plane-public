# ADR-0069: SDK потребителя событий — курсор и дедуп у потребителя, WebSocket как будильник, экспорт в CloudEvents

Статус: Accepted (2026-09-25), фича `notifications`, задача N003 (TASK-000412).
Spec/plan — `specs/notifications/` суперпроекта (FR-011, SC-005); дизайн одобрен
владельцем в TASK-000408. Платформенное решение — TAI-ADR-0049 «Событийная
модель платформы»; серверная часть подписки — [ADR-0068](0068-event-filters-catalog-versions.md).

Контекст: ADR-0023/0024 (непрозрачный курсор, порядок `(tx_id, sequence)`,
сервер при сомнении отдаёт лишнее, а не пропускает), ADR-0068 (подписка = фильтр
чтения, курсор хранит потребитель, серверных подписок нет), ADR-0030 суперпроекта
(клиент — отдельный дистрибутив `control-plane/client`, зависимость — только
`httpx`).

## Контекст

У ядра три потребителя журнала (правила, мост процессов, bidops), и сервис
уведомлений станет четвёртым. Каждый заново решает одно и то же: где хранить
курсор, как не обработать событие дважды после перезапуска, что делать с упавшей
страницей, как узнать о новом событии быстрее опроса. `follow_events` клиента —
только опрос без сохранения позиции и без дедупа: падение посреди страницы
оставляет потребителя перед выбором — потерять хвост страницы или повторить её
начало.

## Решение

1. **`control_plane_client.events.EventConsumer(client, types, workspace_id,
   cursor_store, handler, *, name, …)`.** Читает `GET /events` с фильтрами
   ADR-0068 от курсора хранилища, страницами (`page_size`, 200), и вызывает
   `handler(event)` по одному событию в порядке журнала. `name` — ключ позиции в
   хранилище. `start` задаёт первую позицию, когда курсора ещё нет: `earliest` —
   весь журнал (по умолчанию: ничего не теряется), `latest` — после последнего
   подходящего события (`tail=1`), курсор сразу сохраняется.
2. **Событие — единица работы хранилища.** Протокол `CursorStore`:
   `load(consumer)`, `handle(consumer, event_id, cursor)` — асинхронный
   контекст-менеджер: входит с `False`, если `event_id` у этого потребителя уже
   обработан (событие пропускается), и на чистом выходе записывает отметку
   `event_id` и курсор события вместе; выход исключением не записывает ничего —
   и `advance(consumer, cursor)` — перенос курсора на `nextCursor` страницы
   (через отфильтрованные события, ADR-0068 п.1). Курсор двигается только после
   события, поэтому перезапуск посреди страницы продолжает с первого
   необработанного; отметки по `event.id` делают повторную доставку (повтор
   страницы, перекрытие курсора) пустой.
3. **SQL-хранилище.** `SqlAlchemyCursorStore(engine)` (экстра `[sqlalchemy]`):
   таблицы `<prefix>event_cursors` (`consumer` → `cursor`) и
   `<prefix>handled_events` (`consumer` × `event_id`, `handled_at`); событие —
   одна транзакция, в которую обработчик пишет свои строки через
   `SqlAlchemyCursorStore.session()`. Для эффектов в базе потребителя это
   «ровно один раз»; для внешних эффектов — «хотя бы один раз» с `event.id` как
   ключом идемпотентности. Строка курсора блокируется `FOR UPDATE` на время
   события: два процесса с одним именем не обработают событие оба (первая
   вставка — конфликт первичного ключа, событие повторяется как ошибка).
   Отметки старше `dedup_retention` (7 дней) удаляются при `advance` не чаще
   раза в `prune_interval`: повторная доставка бывает рядом с курсором. Схему
   создаёт миграция потребителя (`cursor_tables(metadata)`), для простых случаев
   — `create_tables()`. `MemoryCursorStore` — в памяти, для тестов.
4. **Повтор, а не пропуск.** Упавшая страница — сеть, `5xx`, исключение
   обработчика (`HandlerError`) — читается заново с сохранённого курсора после
   паузы `retry_initial` (1 с), удваивающейся до `retry_max` (60 с). Отказ в
   самой подписке — `401`, `403`, `404`, `422` при чтении страницы — завершает
   `run()` исключением: повтор его не изменит. Отбросить событие может только
   обработчик — вернувшись без исключения.
5. **WebSocket — будильник, опрос — страховка.** Фоновая задача держит
   `WS /events/ws` с теми же фильтрами и `after` = сохранённый курсор; любой
   кадр только будит цикл чтения, содержимое кадра не обрабатывается —
   источник истины один, `GET /events` + хранилище. Опрос раз в `poll_interval`
   (30 с) покрывает отсутствие сокета; переподключение — с той же паузой, после
   закрытия `4401` обновляется credential, после любого переподключения цикл
   читает один раз вне очереди. Без пакета `websockets` (экстра `[ws]`)
   потребитель только опрашивает.
6. **CloudEvents — функция экспорта.** `to_cloudevent(event, source=None)` —
   CloudEvents 1.0, структурный JSON: `id`, `type`, `time` ← `occurredAt`,
   `subject` = `<entityType>/<entityId>`, `data` ← `payload`; поля конверта без
   пары — расширения `tenantid`, `workspaceid`, `entitytype`, `entityid`,
   `schemaversion`, `actorid`, `correlationid`, `causationid` (пустые
   опускаются: в CloudEvents нет null). `source` по умолчанию —
   `/control-plane/tenants/<tenantId>`. Журнал формат не меняет (ADR-0068 п.4).
7. **Ядро клиента остаётся на `httpx`.** `websockets` и `sqlalchemy` — экстры
   `[ws]`, `[sqlalchemy]`, `[events]` (оба); SQL-хранилище — отдельный модуль
   `control_plane_client.events.sqlalchemy`, импорт `control_plane_client` его не
   тянет.

Отвергнуто: обрабатывать кадры WebSocket как события (два источника позиции,
потерянный при обрыве кадр — потерянное событие); курсор раз в страницу
(падение посреди страницы повторяет её начало); серверные подписки с состоянием
(ADR-0068); дедуп без срока (таблица растёт вместе с журналом).

## Последствия

- Потребитель — сервис уведомлений (N008) и будущий ретранслятор вебхуков —
  получает «без потерь и без повторов» одной зависимостью; своя логика курсора ему
  не нужна.
- Событие стоит одной транзакции в базе потребителя (блокировка строки курсора,
  чтение отметки, вставка, обновление курсора). Для журнала ядра нагрузка та же,
  что у опроса: страница `GET /events` на пробуждение.
- Событие, на котором обработчик падает всегда, останавливает потребителя на
  себе (с растущей паузой и предупреждением в журнале) — это осознанный выбор
  «не терять»; решение отбросить принимает обработчик.
- `follow_events` остаётся для простого чтения без хранилища.
