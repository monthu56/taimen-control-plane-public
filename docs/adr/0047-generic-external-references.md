# ADR-0047: Реестр entity bindings для external references

Статус: Принято (v0.8, TASK-000026)

Расширяет [ADR-0034](0034-external-references.md); границы отображения оттуда
не меняются.

## Контекст

ADR-0034 сделал таблицу product-neutral: внутренняя сторона выражена парой
`entity_type` + `entity_id`, внешняя — `UNIQUE (tenant_id, external_system,
external_type, external_id)`. Generic оказалось только хранилище. Выше него
существовал ровно один тип: HTTP-доступ жил как под-ресурс проекта, команда
принимала `project_id`, требовала `projects.manage` и писала литерал
`entity_type="project"`, обратный поиск был фильтром в списке проектов.

Цена видна снаружи: миграции операционного слоя (ADR-0014 репозитория
документации) негде хранить legacy-идентификаторы задач, и она вынужденно
ввела текстовую конвенцию `SYM-MIG-REF` в описании задачи. Конвенция в
свободном тексте — это индекс, которого нет: дедупликация повторного импорта
опирается на подстроку, обратное отображение требует парсинга описания, а
уникальность внешнего ключа не гарантирована ничем.

## Решение

Ввести явный реестр **entity bindings**: `entity_type` → (загрузчик сущности в
пределах тенанта, permission на чтение, permission на управление). Обобщённая
команда и обобщённые эндпоинты `POST|GET /external-references` работают через
реестр. Проектный скоуп сохраняется как частный случай **того же** кода.

В v0.8 в реестре два типа: `project` (`projects.read` / `projects.manage`) и
`task` (`tasks.read` / `tasks.write`).

### `entity_type` не принимается от клиента как свободный текст

Значение решает три вещи сразу: во что резолвится ссылка, каким правом она
управляется и какой участок общего пространства внешних ключей тенанта
занимает. Поэтому неизвестный тип — `422 invalid_entity_type` до любой записи.
Принимать его как есть означало бы:

- **обход авторизации** — клиент объявляет тип, для которого проверки нет;
- **захват внешнего ключа** — запись на несуществующий тип занимает ключ,
  глобально уникальный в пределах тенанта, и делает честную регистрацию
  невозможной;
- **неразрешимые ссылки** — `entity_id` без известного типа некуда резолвить.

### Право следует типу сущности

Регистрация ссылки на задачу требует `tasks.write` и не требует
`projects.manage`. Harness-ключ с правами на задачи регистрирует
legacy-идентификатор задачи, не получая права переписывать проект.

### Идентичность — пара, а не UUID

«Та же сущность» — это совпадение `(entity_type, entity_id)`. UUID разных
таблиц не образуют общего пространства имён, поэтому совпадение UUID при
разном типе — `409`, а не молчаливое переиспользование ключа.

### Обратный поиск отвечает отсутствием, а не отказом

`GET /external-references?externalSystem=&externalId=` раскрывает `entityType`
и `entityId`, поэтому выдача фильтруется по праву чтения найденного типа, а
недоступное отсутствует в ответе. Различать «ключа нет» и «ключ есть, но не
для тебя» означало бы отдать oracle: перебором чужих внешних идентификаторов
можно установить, какие из них заведены в тенанте. Это тот же принцип единого
ответа, что в [ADR-0045](0045-scoped-tool-discovery.md).

### События остаются на потоке сущности

Тип события выводится из типа сущности:
`<entityType>.external_reference_added|updated`. Для проекта это байт-в-байт
сегодняшние `project.external_reference_*` — существующие подписчики не
затронуты. `metadata` в событие не попадает: это документ, форму которого
задаёт клиент, а поток событий доставляется шире, чем сама строка.

## Последствия

- Схема не меняется: таблица уже была generic, миграции нет.
- Появляется одна точка расширения: типы work item (ADR-0015 репозитория
  документации) добавляются как новые bindings, а не как новые эндпоинты.
- Проектный путь физически вызывает обобщённую команду, поэтому идемпотентность,
  блокировки и семантика конфликта не могут разойтись между скоупами.
- Долг ADR-0014 закрывается: конвенция `SYM-MIG-REF` заменяется записями без
  миграции данных.
- Удаления ссылок через API по-прежнему нет — ограничение ADR-0034 сохраняется.
