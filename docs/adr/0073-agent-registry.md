# ADR-0073: Реестр агентов — ревизии описания, желаемое и фактическое состояние

Статус: Accepted (2026-09-27), фича `declarative-agents`, задача D002
(TASK-000587). Spec/plan — `specs/declarative-agents/` суперпроекта (FR-001…FR-005,
FR-010, FR-012, FR-013; конституция ст. V, VI); дизайн — TASK-000584, ворота
плана одобрены владельцем 2026-09-27 (отступления VI и VIII приняты), разбиение —
TASK-000585. Контракт (маршруты, тела, права, события) опубликован этим шагом
(п.12). Реализован в D005 (TASK-000590, 2026-09-27): таблицы, маршруты,
проверки, `agentRevisionId` на run. Манифесты харнесса
([ADR-0043](0043-effective-harness-manifest.md)) удалены в D007 (TASK-000592,
2026-09-27): миграция `439255fb8627`, маршруты, клиент и MCP-tool. Режим «агент»
у демона исполнителя — D006 (TASK-000591, п.14).

Контекст: TAI-ADR-0052 «Декларативные агенты» (вид каталога `Agent`, схема
`packages/schema/v1` — D001, TASK-000586); TAI-ADR-0018 п.1–3 (реестр
исполнителей в CP, желаемое состояние, агент узла вне ядра); TAI-ADR-0016 п.3–4
(«кто отвечает» и «чей credential расходуется»); TAI-ADR-0044 (пакеты
каталога); ADR-0053 (IAM-связки, отрицательный кэш связок); ADR-0055
(`authorize()`); ADR-0048 и ADR-0072 п.6 (неизменяемые версии, адрес
`key@version`); ADR-0066 (инструкции исполнителю, хэш на run); ADR-0068 (каталог
событий, версии только добавляют поля); CP-ADR-0044 (кооперативная отмена).

## Контекст

Агент сейчас нигде не описан целиком. Личность (principal, связка, права)
заводится скриптом начальной установки. Как агент работает (исполнитель,
модель, отбор работы, соседи, скиллы, лимиты), задают переменные окружения
конкретной машины. Где он работает, решил тот, кто поднял процесс. Ядро не
знает, по какой конфигурации шёл прогон, и не может сравнить описанное с
работающим.

Решение владельца (2026-09-27): агенты описываются декларативно, видом
каталога `Agent` в пакетах. Платформа сама заводит личность, размещает
исполнителя на узле и приводит работающего агента к правке описания. План
делит работу так: реестр описаний и их ревизий — в ядре (этот ADR); узлы,
размещение, выпуск и доставка credential — у `fleet-controller` и `fleet-node`
(TAI-ADR-0018 п.2–3); схема вида — в пакете (TAI-ADR-0052).

Ограничения:

- ядро нейтрально к вендору исполнителя (ст. II), поэтому вид исполнителя для
  него — строка, а его параметры — документ, который ядро не толкует;
- прогон ссылается на неизменяемый снимок (FR-003);
- права в описании не шире прав того, кто его применяет (FR-010, ст. VI);
- значения секретов в ядро не попадают (FR-008).

## Решение

### 1. Агент — объект каталога с ключом

Агент — запись tenant'а с ключом `key` (DNS-метка: `^[a-z0-9][a-z0-9-]*$`, до 63
символов). Тело `POST /api/v1/agents` — объект каталога без конверта:
`{key, spec}`, где `spec` — ровно `spec` файла пакета вида `Agent`. Установщик
пакетов (`cp_packages`, D011) снимает `apiVersion`/`kind`, подставляет
переменные установки `${…}` и больше ничего не меняет.

Поля `spec`, и кто их толкует. Имена и форма — схема вида каталога
(`$defs.agentSpec` в `packages/schema/v1/object.schema.json` суперпроекта), ядро
описывает тот же объект моделью `AgentSpec` (`api/v1/schemas.py`):

| Поле | Толкует | Что проверяет ядро |
|---|---|---|
| `displayName`, `description?` | ядро | строка 1…200; описание ≤ 2000 |
| `identity {kind: agent\|service, roles, permissions, capabilities}` | ядро | `kind` обязателен; права — `^[a-z_]+(\.[a-z_]+)+$`, в каталоге и не шире прав применяющего (п.5); роли — slug; роли и capabilities существуют |
| `identity.iam {audiences, scopeCeiling}` | тот, кто выпускает учётку в IAM (bootstrap суперпроекта, `fleet-controller`) | только форма: раздел необязателен при любом `identity.kind`; `audiences` — 1…20 уникальных строк 1…100; `scopeCeiling` — 1…50 уникальных scope `^[a-z][a-z0-9-]*:[a-z][a-z0-9-]*$` (`<audience>:<действие>`, например `control-plane:read`) |
| `work {workspace?, project?, includeSubprojects, onlyAssigned, taskTypes}` | ядро и демон исполнителя | все поля необязательны; `includeSubprojects` — `false` по умолчанию; workspace и проект — id, существуют; типы задач tenant'а существуют |
| `executor {kind, params, instructions}` | адаптер вида | `kind` — строка `^[a-z][a-z0-9-]*$`; `params` — объект, ядро его не толкует; `instructions` ≤ 64 KiB |
| `workingCopy {repository, directory?, baseRef?, neighbours, superproject?, publish, review?}` | демон исполнителя (TAI-ADR-0016 п.5) | форма: `repository` обязателен; `directory` и имена соседей — `^[a-z0-9][a-z0-9._-]*$`; `review {mode: human\|agent\|none, taskType, taskTypes, reviewer, base}` |
| `skills {protocols, local, httpOrigins, mcpOrigins, audiences, concurrency}` | демон исполнителя | `protocols` ⊆ `local`/`http`/`mcp`; `local` — entrypoint или пакет; `concurrency` 1…32 |
| `placement {requires, secrets, resources, replicas, drainSeconds}`, `none` или нет поля | fleet-controller | форма: `requires` — метка узла `имя` или `имя=значение` (`^[a-z0-9][a-z0-9.-]*(=[a-zA-Z0-9._-]+)?$`); `secrets` — имена `^[a-z0-9][a-z0-9-]{0,62}$`; `resources {cpus, memoryMb}`; `replicas` 0…20; `drainSeconds` 0…14400 (предел run) |
| `state: running\|stopped` | ядро (п.3) | перечисление |

Неизвестное поле в любом разделе, кроме `executor.params`, — `400
invalid_request`: опечатка в `onlyAssigned` не должна молча превращаться в
«брать любую работу». Параметры вида проверяет схема вида из пакета
(`$defs.agentExecutors.<kind>`, TAI-ADR-0052) и адаптер, ядро их не толкует.
Описание без размещения (`placement: none`: сервисная учётка, мост
process-runtime) может не иметь `executor` и `work`. Нет поля `placement` —
агент размещается с умолчаниями, и ему, как любому размещаемому, `executor`
обязателен.

`identity.iam` (D014a) — IAM-часть сервисной учётки: audiences и потолок scope
service account'а, которые выпускает bootstrap суперпроекта (мост
process-runtime, notification-service, fleet-controller описаны видом `Agent`,
`kind: service`, `placement: none`). Ядро хранит раздел как данные описания и
не толкует: учётку в IAM выпускает не ядро, и токен с этим потолком ядро видит
только как IAM-идентичность связки. Principal и связку ядро выводит так же, как
для любого агента, — по `PUT /agents/{key}/identity` (п.6), с правами из
`identity.permissions`, а не из `scopeCeiling`. Раздел входит в ревизию и её
хэш, как остальные (п.2); описание без `iam` хэшируется как прежде, поэтому
хэши существующих ревизий не меняются.

Ядро строже схемы вида в двух местах: `identity.permissions` не пуст (агент без
прав не прочтёт даже свою задачу), и дробное `resources.cpus` схема принимает,
а канонизация ревизии (п.2) — нет.

Схема вида и `AgentSpec` описывают один объект, и contract-тест
(`tests/unit/test_agent_contract.py`) держит их вместе:

- примеры схемы вида (`tools/tests/test_agent_schema.py` суперпроекта: по
  одному на `claude-code`, `codex`, `skills` и `placement: none`) лежат в
  `tests/fixtures/agents/`; каждый принимает схема вида и `AgentSpec`, и
  выгрузка `AgentSpec` возвращает его без изменений;
- документы, которые схема вида принимает (без `placement`, метки `имя=значение`,
  `includeSubprojects`, `mcpOrigins`, …), ядро принимает без изменений;
- документы, которые она отвергает (размещённый без `executor`, `workspace`
  вместо `workingCopy`, `skills.concurrency` вне 1…32, метки и секреты вне
  паттерна, …), ядро тоже отвергает.

Схему тест берёт из суперпроекта, когда control-plane лежит в нём сабмодулем
(`../packages/schema/v1/object.schema.json`), иначе — из закреплённой копии
`tests/fixtures/superproject/object.schema.json`. В суперпроекте тест сверяет и
копию: расхождение `$defs` вида `Agent` роняет тест, и копию обновляют вместе с
`AgentSpec`.

### 2. Ревизии: неизменяемый снимок и хэш канонического JSON

Каждое применённое изменение описания — новая ревизия агента (`agent_revisions`):
номер с 1 внутри ключа, `spec`, `specHash`, `createdBy`, `createdAt`. Ревизия не
меняется и не удаляется.

- **Что хэшируется.** Хэшируется `spec` в том виде, в каком его прислали:
  без подстановки умолчаний, но без полей желаемого состояния (`state` и
  `placement.replicas`, п.3). Хэш — `sha256:<hex>` канонического JSON по
  правилам `domain/canonical.py`: ключи отсортированы, без пробелов, строки
  NFC, UTF-8. Числа с плавающей точкой запрещены, поэтому ресурсы задаются
  целыми (`cpus: 2`, `memoryMb: 4096`); дробное `cpus` — `422
  non_canonical_value`. Предел длины строки для `spec` —
  64 KiB, а не общие 2000 символов: в `executor.instructions` живут
  соглашения исполнителя. Весь `spec` — до 256 KiB.
- **Когда появляется ревизия.** Новая ревизия появляется, только если хэш
  отличается от хэша текущей. Повторное применение того же файла — `200`, без
  ревизии и без события. Первое описание ключа или изменённое — `201`,
  событие `agent.revision_published`.
- **Откат.** Прежнее описание, применённое снова, даёт новую ревизию N+1 с тем
  же хэшем, что у N−1: история линейна, откат виден в журнале (сценарий 2.4).
- **Адрес.** `GET /agents/{key}` — агент с текущей ревизией,
  `GET /agents/{key}@{revision}` — с указанной. Нет такой — `404`.
- **Выгрузка в формат пакета** (FR-012, SC-007): `revision.spec` плюс `state`
  и `placement.replicas` из желаемого состояния на их места. Отдельного
  маршрута нет: `AgentOut` содержит всё нужное, а оболочку
  `{apiVersion, kind, key}` добавляет установщик.

### 3. Желаемое состояние — отдельно от ревизии

`state` (`running|stopped`) и `replicas` хранятся в записи агента, а не в
ревизии: остановка агента не порождает новую конфигурацию, а новая ревизия не
теряет остановку.

- `POST /agents` применяет `spec.state` и `spec.placement.replicas` в той же
  транзакции, что и ревизию: пакет — источник истины, и ручная остановка в
  обход пакета перетирается следующим применением (пограничный случай spec).
- `PATCH /agents/{key}/state {state?, replicas?}` (`agents.manage`) меняет
  только желаемое состояние. Нужно хотя бы одно поле.
- Изменение — событие `agent.state_changed`. Без изменения события нет.

### 4. Фактическое состояние пишет только служба размещения

`agent_status` — одна строка на агента: `phase`, `reason {code, message}`,
`observedRevision`, `node` (имя узла — данные fleet, ядро его не толкует),
`instances {desired, ready}`, `observedAt`, `reportedBy`.

| `phase` | Значение |
|---|---|
| `pending` | размещён, исполнитель ещё не поднялся |
| `running` | работает (`instances.ready ≥ 1`) |
| `waiting_for_node` | подходящего узла нет; `reason.code`: `no_matching_node`, `missing_secret`, `no_capacity`… |
| `crash_looping` | падает при запуске; узел перезапускает с растущей паузой, `reason` — последняя причина |
| `node_unavailable` | узел размещения перестал отчитываться, переезд не удался |
| `stopped` | остановлен по желаемому состоянию |

- `PUT /agents/{key}/status` требует `agents.status.write`. Это право получает
  только service account `fleet-controller`, администратор каталога его не
  имеет. «Работает» в ядре — всегда слова службы, которая это видит.
- Отчёт старше сохранённого (`observedAt` меньше) — `409
  stale_status_report`: ответы узлов приходят не по порядку.
- Отчёт о ретайрнутом агенте — `409 agent_retired`.
- Событие `agent.status_changed` пишется, только если изменились `phase`,
  `reason.code`, `node` или `observedRevision`. Отчёты раз в 20 секунд без
  изменений журнал не засоряют.
- `GET /agents/{key}/status` (`agents.read`) отвечает `phase: unknown`, пока
  отчёта не было. У агента с `placement: none` фаза остаётся `unknown`.

### 5. Права и проверка «права ревизии ⊆ права применяющего»

Новые права (`Permission`, `authz/catalog.yaml`, ресурс — tenant):

- `agents.read` — список, агент, ревизия, фактическое состояние;
- `agents.manage` — `POST /agents`, `:validate`, `PATCH …/state`, `:retire`;
  администратор каталога;
- `agents.status.write` — `PUT …/status` и `PUT …/identity` (п.6); только
  service account `fleet-controller`. `agents.manage` его не включает, и
  наоборот.

`GET /agents/me` требует только аутентификации: исполнитель читает своё
описание, и отдельного права для этого не нужно.

Проверки `POST /agents` и `:validate` идут до любой записи (FR-010). Ошибка
возвращается в едином конверте:

1. Форма — `400 invalid_request`.
2. Ключ ретайрнут — `409 agent_retired`. Ключ не переиспользуется: его история
   и прогоны остаются за ним.
3. Права `identity.permissions`:
   - неизвестные — `422 invalid_permissions`;
   - `admin` может выдать только администратор — `422 invalid_permissions`;
   - права только для человека (`admin`, `approvals.decide`) у `agent` и
     `service` — `422 permissions_not_allowed_for_kind`;
   - каждое право должно быть у применяющего (администратор — исключение),
     иначе `403 permission_escalation` с `details.missing`.

   Это та же проверка, что у `iam-bindings` (ADR-0053), и одна функция на
   оба места.
4. `identity.roles` и `identity.capabilities`: у применяющего должно быть
   `org.manage` — то же право, которым назначают роли и capabilities сейчас.
   Иначе `403 permission_escalation`. Ссылка на несуществующую роль или
   capability — `422 unknown_reference` с `details.path`.
5. `work`: workspace, проект и типы задач существуют, а workspace виден
   применяющему. Иначе `422 unknown_reference`.
6. Секреты:
   - ключи в `executor.params`, `workingCopy` и `placement.resources`
     проверяются общим `reject_secret_material` — `422
     secret_material_rejected`;
   - `placement.secrets` — список имён, это разрешённая ссылка на секрет
     узла, а не значение, и общая проверка к нему не применяется.
7. Канонизация (п.2) — `422 non_canonical_value` или `payload_too_large`.

Проверка идёт при каждом применении, даже если хэш не изменился. Иначе
`:validate` и `POST` отвечали бы по-разному, а повторное применение пакета
узкой учёткой прятало бы то, что она описывает права шире своих.

`POST /agents:validate` выполняет ровно эти проверки и ничего не пишет. Ответ:
`{key, specHash, currentRevision, wouldCreateRevision, wouldChangeState}`.
Неуспех — та же ошибка, что вернул бы `POST`: конструктору и пакету нужен один
путь (сценарий 6).

### 6. Личность агента — производная ревизии, связку держит ядро

План (п.4 «Исследования») отдавал заведение principal и связки в ядре
`fleet-controller`. Этот ADR уточняет разделение.

Правило `iam-bindings` (ADR-0053) «связка выдаёт только права, которые есть у
выдающего» потребовало бы у контроллера все права всех агентов, то есть
фактически `admin` в CP. Это противоречит ст. VI и узкому scope `iam:agents`,
ради которого принималось отступление VI. Права ревизии уже проверены против
применяющего (п.5), поэтому связку по ревизии создаёт само ядро.

- `fleet-controller` по событию `agent.revision_published` заводит principal
  в IAM (scope `iam:agents`) и выпускает PAT. Затем он сообщает ядру
  IAM-идентичность: `PUT /agents/{key}/identity {issuer, iamTenantId,
  iamPrincipalId}` (`agents.status.write`).
- Ядро в одной транзакции:
  - заводит principal CP вида `identity.kind` с `displayName` описания и
    `metadata.agentKey`;
  - назначает роли и capabilities;
  - создаёт IAM-связку с `identity.permissions` текущей ревизии;
  - записывает `agents.principal_id`.

  После фиксации ядро сбрасывает кэш связок для этой идентичности, включая
  отрицательный: новый агент входит без перезапуска API. Пишутся обычные
  события `principal.created` и `iam_binding.*`.
- `PUT …/identity` идемпотентен. Повторная привязка той же идентичности —
  `200` без изменений: второй principal, вторая связка и повторные события не
  появляются. Контроллер вправе повторять вызов после сбоя или таймаута, не
  зная, дошёл ли первый: всё делается в одной транзакции, и частично
  выполненной привязки не бывает. Другая идентичность у уже привязанного
  агента — `409 agent_identity_conflict`: смена личности — это вывод из
  оборота и новый ключ.
- Это отличие от плана: там principal и связку заводил `fleet-controller`,
  здесь их выводит ядро по `PUT /agents/{key}/identity`. Отличие принято на
  ревью D002 (TASK-000609) при условии идемпотентности выше; D005 проверяет её
  integration-тестом (повтор, повтор после отката).
- Новая ревизия с другим `identity` приводит связку и назначения к ней в той
  же транзакции, что публикует ревизию (revoke и новая связка, разница ролей).
  Ядро не ждёт контроллера и не оставляет окна, когда ревизия уже новая, а
  права ещё старые.
- Полномочие связки — полномочие применившего ревизию (`createdBy`). Если
  потом у него отзовут права, выданное агенту не отзывается: так же ведут себя
  ключи и связки сейчас.

### 7. Ревизия на прогоне

Колонка `runs.agent_revision_id` (nullable, FK на `agent_revisions`) и поле
`agentRevisionId` в `RunOut`. В теле `POST /tasks/{ref}:start-run` появляется
`agentRevisionId` (необязательное по схеме):

- principal, привязанный к активному агенту, обязан передать ревизию своего
  агента. Без неё — `422 agent_revision_required`, с чужой — `422
  agent_revision_mismatch`;
- ревизия своего агента, но не текущая, принимается: исполнитель узнаёт о
  новой ревизии между прогонами, и гонка публикации со стартом не должна
  ронять работу. Записывается то, по чему прогон идёт на самом деле;
- principal, не привязанный к агенту (человек, прежний раннер), ревизию не
  передаёт. Переданная — `422 agent_revision_mismatch`.

`run.started` получает `agentRevisionId` версией 2 схемы события вместе с
писателем (D005): версия в каталоге и поле в записи появились одновременно.
Проверка ревизии идёт до блокировки задачи и до проверки claim.

### 8. `GET /agents/me`

Ответ — агент вызывающего principal (`agents.principal_id`) с текущей ревизией
и желаемым состоянием, тот же `AgentOut`. Principal не привязан к агенту —
`404 not_found`. Ретайрнутый агент отдаётся со `status: retired`: исполнитель
должен узнать об этом и завершиться, а не получить невнятный `404`.

Демон исполнителя строит настройки из ответа. Между прогонами он сверяет
ревизию и при смене завершается кодом 75 после текущего прогона (план,
«Исследование» п.2). Это поведение демона, не ядра.

### 9. Вывод из оборота

`POST /agents/{key}:retire {reason}` (`agents.manage`) в одной транзакции:

- `status: retired`, `state: stopped`;
- связки principal агента отзываются, principal переводится в `disabled`, но
  не удаляется: на нём история прогонов и журнала;
- активные claim'ы principal отпускаются, задачи возвращаются в очередь по
  правилам отпущенного claim;
- событие `agent.retired` (`releasedClaims`, `reason` с редакцией и пределом,
  как у прочих причин в журнале).

`fleet-controller` по событию останавливает исполнитель и отзывает PAT в IAM.

Повтор — `200` без нового события. Ревизии, фактическое состояние и прогоны
остаются. Публикация в ретайрнутый ключ — `409 agent_retired`.

### 10. События

| Тип | Когда | Payload |
|---|---|---|
| `agent.revision_published` | новая ревизия (п.2) | `key, revision, specHash, previousRevision, executorKind, placed, permissionsChanged` |
| `agent.state_changed` | изменилось `state` или `replicas` (п.3) | `key, state, replicas, previousState, previousReplicas` |
| `agent.status_changed` | изменились `phase`, `reason.code`, `node` или `observedRevision` (п.4) | `key, phase, previousPhase, reasonCode, node, observedRevision, observedAt` |
| `agent.retired` | вывод из оборота (п.9) | `key, revision, principalId, reason, releasedClaims` |

`entityType` — `agent`, `entityId` — id агента, `workspaceId` конверта —
workspace из `work` (нет `work.workspace` — `null`). `actorId` отвечает на
вопрос «кто применил ревизию» (FR-013). Каталог (`domain/event_catalog.py`,
`docs/events/`) публикует схемы уже сейчас, `spec` целиком в событие не кладётся.
Потребитель берёт ревизию по `GET /agents/{key}@{revision}` с `agents.read`.

### 11. Чего в ядре нет

Ядро не знает:

- об узлах, их метках, ёмкости и здоровье;
- о размещении;
- о PAT агента и его шифровании;
- о значениях секретов;
- об образах видов исполнителей.

Всё это — `fleet-controller` и `fleet-node` (TAI-ADR-0018 п.3, отдельный
репозиторий `fleet`). Имя узла попадает в ядро только как строка отчёта
(п.4). Вид исполнителя — строка без перечисления в коде ядра: новый вид — это
схема в пакете и образ на узле, а не изменение ядра.

### 12. Контракт до реализации

Маршруты `/agents` были объявлены в `api/v1/agents.py` и опубликованы в OpenAPI
до реализации. До D005 каждый проверял своё право и отвечал `501
not_implemented`. D005 заменил тела обработчиков и не изменил подписи.

### 13. Уточнения реализации (D005)

- `identity.roles` — slug'и ролей уровня tenant'а (`workspace_id IS NULL`);
  роли, заведённые внутри workspace, описанием не назначаются.
  `identity.capabilities` — имена capabilities.
- `work.workspace` — id или slug. Slug уникален только среди соседей, поэтому
  slug, который называет несколько workspace, отклоняется как
  `unknown_reference`, а не угадывается. `work.project` — id проекта, id или
  slug его workspace. `work.taskTypes` — ключи, у которых есть активная версия.
- Ревизия хранит и хэширует `spec` в том виде, в каком он прислан, без
  подстановки умолчаний. Из него вынимаются `state` и `placement.replicas`.
  Нет поля `placement` — агент размещаемый, `replicas` равно 1 (п.1); у
  описания с `placement: none` `replicas` равно 0. Нет `work` или
  `work.workspace` — `workspaceId` агента `null`.
- Секреты в `workingCopy` ищет тот же `reject_secret_material` (п.5): по
  именам ключей, в том числе в `neighbours`.
- У связанного агента сменить `identity.kind` нельзя: `409
  agent_identity_conflict`, как и смена IAM-идентичности (п.6). Проверка идёт
  вместе с остальными, поэтому `:validate` отвечает так же.
- Новая ревизия связанного агента приводит связку к новым правам на месте:
  связка — одна строка на `(issuer, iamPrincipalId)`, поэтому пишется
  `iam_binding.updated`, а не revoke и новая связка. Роли и capabilities
  приводятся разницей (`role.assigned|revoked`, `capability.assigned|revoked`).
- Первое применение ключа пишет и `agent.revision_published`
  (`permissionsChanged: true`), и `agent.state_changed` с
  `previousState: null`. Схема v1 `agent.state_changed` разрешала `null` в
  `previousState` только по типу, но не по перечислению. Это исправлено в той
  же версии: до D005 событие не писалось.
- Кэш связок сбрасывается после фиксации транзакции у `PUT …/identity`, у
  публикации, которая изменила права связанного агента, и у `:retire`. Сброс
  тот же, что у `iam-bindings` (ADR-0053), включая отрицательный ответ,
  закэшированный до появления связки.
- При выводе из оборота claim'ы principal агента отпускаются по держателю
  (`holder_id`), а не по сессии: общая функция `_claim_release`.

### 14. Исполнитель из ревизии (D006)

Демон `control-plane-agent` (`control_plane_agent/revision.py`) решает при
старте, чей он. `CONTROL_PLANE_AGENT_CONFIG`:

- `auto` (по умолчанию) — `GET /agents/me`: есть агент — режим агента,
  `404` — env-режим как раньше (локальная отладка, прежние раннеры);
- `revision` — агент обязателен, без него выход 2;
- `env` — только окружение, для principal без агента.

`auto` — не удобство: principal агента обязан называть ревизию в `start-run`
(п.7), в env-режиме он не запустил бы ни одного прогона. Ошибка чтения `me`
при старте — выход 75: процесс не угадывает режим, его перезапускают.

**Что берётся из ревизии.** Разделы `spec` становятся аргументами, которые
демон и его части уже принимали:

| Раздел | Во что |
|---|---|
| `work` | workspace — `workspaceId` агента (ядро уже разрешило slug), `project`, `includeSubprojects`; `onlyAssigned` — по умолчанию `true`, как в схеме вида (в env-режиме — `false`); `taskTypes` — фильтр по `typeKey` поверх `/work/available` |
| `executor.kind` | `claude-code`, `codex` — адаптер из `params`; `skills` — без адаптера: обычная работа не берётся, только работа, которую исполняет скилл, и вызовы скиллов; `echo` — эталонный адаптер протокольных тестов, без `params`; иное — выход 2 |
| `executor.params` | проверяет адаптер (`adapter_from_params`): неизвестный или неверный параметр — выход 2, а не умолчание. Claude Code: `model`, `permissionMode`, `timeoutSeconds`, `resume`, `tools.allow/deny`; Codex: `model`, `sandbox`, `timeoutSeconds`, `resume`, `credentialClass` |
| `executor.instructions` | четвёртый слой инструкций (CP-ADR-0066) вместо файла `CONTROL_PLANE_*_PROMPT_FILE` |
| `workingCopy` | пул рабочих копий: `repository`, `neighbours`, `superproject` — URL, копии режутся из bare-зеркал хоста (`CONTROL_PLANE_AGENT_MIRRORS`, по умолчанию `<корень копий>/.mirrors/<имя>.git`); зеркало хоста берётся, если его `origin` — тот же URL, чужое — выход 2, нет зеркала — `git clone --bare`. Путь к каталогу на хосте берётся как есть. `publish` (по умолчанию `true`) — публикация в `origin` зеркала; `baseRef`, `directory` |
| `workingCopy.review` | политика авто-ревью (ADR-0052): `mode` (`agent` по умолчанию, `none` — без ревью), `taskType`, `taskTypes`, `reviewer`, `base`; `human`/`agent` без `reviewer` — выход 2 |
| `skills` | исполнитель скиллов: `protocols`, `local`, `httpOrigins`, `mcpOrigins`, `audiences`, `concurrency`. Чего нет в описании, того нет и у исполнителя, даже если оно задано на хосте |
| `placement.drainSeconds` | время на прогон в полёте при остановке (ниже); `placement: none` — ждать сколько нужно |

Хосту остаётся своё: адрес ядра и credential, корень рабочих копий и
зеркал, бинарники CLI, проброс MCP, локальные логи, переключатели трассы,
изоляция локальных скиллов, доверенные внутренние хосты, stdio-серверы MCP,
сторож прогресса.

**Набор инструментов Claude.** `tools.deny` добавляется к запрету
авторитетных команд CP (`--disallowedTools`), `tools.allow` уходит в
`--allowedTools` без авторитетных команд. Запрет снимается только правкой
MCP-сервера, не описанием: CLI и так даёт запрету победить, но argv не должен
утверждать обратного.

**Ревизия на прогоне и её смена.** Процесс работает по одной ревизии, с
которой стартовал, и называет её в `start-run` каждого прогона. Между
прогонами (сразу после прогона, в простое — не чаще раза в 30 с) он читает
`me` снова:

- другая ревизия — завершение с кодом **75** (`EX_TEMPFAIL`): тот, кто
  разместил процесс, запускает его на новой. Прогон в полёте доводится по
  старой ревизии, новых демон не берёт; две ревизии в одном процессе не
  смешиваются;
- агент выведен из оборота или `state: stopped` — завершение с кодом 0;
- ошибка чтения — работа продолжается, спросит в следующий раз.

**Остановка и `drainSeconds`.** `SIGTERM`/`SIGINT` — демон перестаёт брать
работу, прогон в полёте получает `placement.drainSeconds` (по умолчанию
14400 — предел run). Не успел — сторож прогона (`supervision.py`)
останавливает исполнителя тем же путём, что и запрос отмены (CP-ADR-0044):
процесс CLI убивается, run завершается `cancelled` с причиной `drained`,
claim отпускается, задача возвращается в очередь для следующего экземпляра,
а не ждёт истечения аренды. Сигнал о новой ревизии не нужен: к моменту
выхода с кодом 75 прогона в полёте нет. В env-режиме то же задаёт
`CONTROL_PLANE_AGENT_DRAIN_SECONDS`; без неё, как раньше, прогон доводится
до конца.

Узел должен давать процессу после `SIGTERM` не меньше `drainSeconds` плюс
запас на отмену (опрос прогона — до 30 с): иначе `SIGKILL` оставит run
`running` до истечения аренды, и его разберёт восстановление при
следующем старте (`restart_recovery`).

Клиент SDK получил методы реестра: `get_my_agent`, `get_agent`,
`list_agents`, `publish_agent`, `validate_agent`, `update_agent_state`,
`retire_agent`, `link_agent_identity`, `get_agent_status`,
`report_agent_status`, и `agent_revision_id` у `start_run`.

## Границы

- Бюджеты, иерархия агентов и наём с одобрением (TAI-ADR-0009,
  TAI-ADR-0018 п.4–5) не вводятся. В ревизии для них есть место, но нет полей.
- Автомасштабирование по очереди не вводится: `replicas` задаётся описанием.
- Исполнители вертикального пакета BidOps и персональный харнесс человека не
  описываются (решение владельца на дизайне).
- Общих узлов нескольких tenant'ов нет: реестр — данные одного tenant'а.
- Отдельного журнала ревизий (`GET /agents/{key}/revisions`) нет: адрес
  `key@revision` и события `agent.revision_published` покрывают сценарии
  spec. Список добавляется, когда появится потребитель.

## Последствия

- Конфигурация исполнителя — данные tenant'а с историей. Прогон называет
  ревизию, по которой шёл (SC-003), а работающее сравнивается с описанным
  через `status.observedRevision`.
- Службе размещения нужны только `agents.read` и `agents.status.write`. Прав
  выдавать права у неё нет (п.6).
- Манифесты харнесса [ADR-0043](0043-effective-harness-manifest.md) теряют
  смысл: конфигурация исполнителя — ревизия агента. ADR-0043 получает статус
  «заменён CP-ADR-0073», поверхность удалена (D007): таблицы, маршруты
  `/runs/{id}/harness-manifest*`, метод клиента, MCP-tool `cp_harness_manifest`.
  Типы событий `run.manifest_*` остаются в каталоге для уже записанных
  событий (CP-ADR-0068), но не пишутся.
- Ядру нужен второй предел длины строки канонического JSON (п.2). Общие 2000
  символов остаются для манифестов и ревизий инструментов.
