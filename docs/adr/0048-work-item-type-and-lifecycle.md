# ADR-0048: Тип work item и настраиваемый lifecycle

Статус: Accepted (v0.8, TASK-000025)

Контекст: ADR-0015 «Модель work item» верхнего уровня, «Решение» п.1-2;
прецедент — ADR-0030 (immutable project templates) и ADR-0031 (пара
«пользовательский статус + системная категория»).

## Контекст

Task не имела типа, а её состояние было прибито `CHECK (status IN (...))` на
шесть значений. Ядро принимало решения по ключу этого перечисления: claim
отказывал при `done|cancelled`, переводил `todo|backlog` в `in_progress`,
снятие claim возвращало `in_progress` в `todo`, завершение писало литерал
`done`, а предусловие считалось выполненным при `status = 'done'`.

Следствие: вопрос, операция и инцидент не имели дома. ADR-0014 показал это
численно — 93 из 241 переносимой сущности мигрировали как Task с конвенцией в
тексте, а состояния `review`, `answered`, `approved`, `rolled_back` не
выражались вовсе.

Для Workspace и Project этот же класс задачи уже был решён. Здесь мы переносим
решение на work item, не изобретая второго механизма.

## Решение

1. **Реестр `task_types`** — tenant-scoped, версионируемый, с `field_schema` и
   `lifecycle_schema`. Форма и гарантии повторяют `project_templates`: версия
   уникальна в пределах `(tenant, key)` и иммутабельна после INSERT; триггер
   `forbid_task_type_mutation` пропускает только `active -> deprecated`.
   Редактирование типа — всегда новая версия.

2. **Статус задачи — пара.** `tasks.status` остаётся пользовательским ключом;
   рядом появляется `tasks.system_status_category` из закрытого словаря:

   | Категория | Смысл |
   |---|---|
   | `backlog` | не готова к взятию |
   | `active` | в работе или готова к взятию |
   | `blocked` | ожидает внешнего условия |
   | `terminal_success` | завершена успешно |
   | `terminal_cancelled` | закрыта без результата |

   Ядро ветвится **только по категории**. Тенант вправе назвать статус `done`
   и дать ему категорию `active` — и ядро будет считать такую задачу активной.
   Это не дефект, а прямое следствие решения.

3. **Переход только по объявленному ребру**, под `If-Match` и существующим
   claim-gate. Отказ не меняет ни статус, ни версию.

4. **Три служебных статуса в `lifecycle_schema`** — `claimStatus`,
   `releaseStatus`, `completionStatus`. Это то, чем становятся сегодняшние
   литералы `in_progress`, `todo`, `done`. `claimStatus` и `releaseStatus`
   обязаны быть нетерминальными; `completionStatus` обязан иметь категорию
   `terminal_success` и выводится автоматически, если такой статус ровно один.

5. **Автоматический переход применяется только по объявленному ребру, иначе
   пропускается.** Claim и его снятие остаются успешными. Отказать в claim
   из-за необъявленного ребра означало бы превратить косметику конфигурации в
   отказ в обслуживании: авторитетным механизмом координации является claim с
   lease и fencing, а не подпись под ним. Завершение — исключение: это явное
   действие пользователя, и необъявленное ребро отклоняется.

6. **Системный тип `task`** создаётся каждому тенанту миграцией и bootstrap:
   шесть прежних статусов и граф, полный на четырёх нетерминальных. Поэтому ни
   один существующий переход не становится незаконным.

7. **Отдельные права** `task_types.read` и `task_types.manage`. Право менять
   словарь состояний тенанта не следует из права заводить задачи.

## Границы

- `custom_fields` задачи и применение `field_schema` — WI-3; колонка заводится
  пустой и ни к чему не применяется;
- плановые даты, комментарии, метки, ранжирование, watchers — вне решения;
- смены типа существующей задачи нет: она требует отображения статусов старого
  lifecycle в новый, а это отдельное решение;
- категория `blocked` **не** запрещает claim — сохранено сегодняшнее
  поведение; запрет был бы продуктовым изменением, а не рефакторингом.

## Не принято

- **Колонка `is_system` по образцу `workspace_types`.** Для версионируемой
  таблицы инвариант «ровно один системный ключ» не выражается индексом:
  частичный уникальный индекс по `(tenant_id)` запретил бы вторую версию,
  а по `(tenant_id, version)` не запретил бы второй системный ключ. Роль
  fallback несёт константа ключа, а защита приходит из иммутабельности версий.
- **Единый словарь категорий с проектом.** «Пауза проекта» и «блокировка
  задачи» — разные вещи; общий словарь обслуживал бы оба смысла плохо. Общими
  остаются разбор, дата-класс `Lifecycle` и обе терминальные категории.
- **Свободный статус без реестра.** Тогда ядро не смогло бы вывести категорию,
  и решение по категории выродилось бы в решение по строке.
- **Проверка достижимости финала из каждого статуса.** Превращает конфигурацию
  в задачу на графах и запрещает промежуточные состояния, которые тенант
  заполняет постепенно.
- **Завершение через `PATCH status`.** Завершение снимает claim, разбирается с
  running run и пишет `completed_at`; статус — только один из его эффектов.

## Последствия

- решения ядра перестают зависеть от названий статусов: проект может ввести
  свой процесс, не трогая core;
- база больше не знает словаря статусов. Это не ослабление: шесть значений в
  `CHECK` никогда не проверяли **соответствие** статуса типу, потому что типа
  не было. Проверка переехала в приложение под блокировку строки, туда же, где
  живёт проверка статуса проекта;
- появляется вторая конфигурируемая подсистема со схемами и версиями; растёт
  цена валидации и миграций;
- **downgrade миграции необратимо теряет пользовательские ключи статусов**:
  шестизначный `CHECK` не примет `review`, и ключ схлопывается на легаси-ключ
  своей категории. Downgrade документирован как аварийный путь;
- единственное сужение контракта — переход «в тот же статус» теперь
  отклоняется (унификация с моделью проекта).
