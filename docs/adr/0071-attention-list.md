# ADR-0071: «Важное» человека — `GET /me/attention` и обратная связь

Статус: Proposed (2026-09-26), фича `human-harness`, задача H003
(TASK-000496). Spec/plan — `specs/human-harness/` суперпроекта (FR-002;
SC-002, SC-003, SC-005; ст. III, IV конституции); правила — plan,
§«Исследование» п.4. Ворота плана одобрены владельцем 2026-09-26. Принимается
ревью задачи. Потребители — экран «Важное» харнесса человека (H006) и
проактивность (H009).

Контекст: ADR-0018 (approvals, gate и право решать), ADR-0048 (статусы — словарь
типа, ядро ветвится только по категории), ADR-0049 (плановые даты), ADR-0055
(`authorize`, режимы local/shadow/policy), ADR-0067 (критерии `human` —
решение gate-approval), ADR-0068 (каталог событий).

## Контекст

Харнесс человека показывает одно окно: беседу и «Важное» — то, что ждёт
человека сейчас. Собирать этот список на стороне харнесса значит повторять
правила пригодности approval (роль в поддереве workspace), вид задач по
категориям и счёт прогонов — в каждом клиенте заново, с чужими правами и с
риском показать чужое. Ядро знает все нужные факты. Нужен один запрос с
объяснимыми элементами («почему это здесь») и способ сказать «это не нужно
было показывать», чтобы правила можно было мерить и править.

## Решение

### 1. Запрос

`GET /api/v1/me/attention?workspaceId=&includeDescendants=` — список
вызывающего, отсортированный по `score` по убыванию (при равенстве — раньше
возникшее выше). Без пагинации: список короткий по смыслу, каждое правило
отдаёт не больше 100 элементов (п.5). `workspaceId` ограничивает элементы
workspace объекта (у approval — его workspace, иначе workspace задачи),
`includeDescendants=true` — поддеревом; неизвестный workspace — 404, как у
`GET /tasks`. Ответ:

```json
{
  "items": [{
    "itemKey": "approval.review:<uuid>",
    "kind": "review",
    "reasonCode": "review_role",
    "rule": "approval.review@1",
    "score": 80,
    "entity": {"type": "approval", "id": "<uuid>"},
    "title": "…", "workspaceId": "…", "taskId": "…", "taskPublicId": "TASK-000123",
    "dueDate": null, "since": "2026-09-26T07:00:00Z",
    "details": {"requestedBy": "…", "requiredRoleId": "…", "comment": "…"},
    "actions": [{"action": "approve", "method": "POST", "href": "/api/v1/approvals/<uuid>:approve"}, …],
    "feedback": null
  }],
  "degraded": [{"rule": "task.blocked@1", "reasonCode": "rule_failed", "message": "…"}],
  "generatedAt": "…"
}
```

Список вычисляется при каждом чтении и не хранится. `itemKey` =
`<ruleKey>:<entityId>`: он стабилен, пока правило поднимает тот же объект, и
не зависит от версии правила. `rule` = `ruleKey@version`: изменение того, что
правило выбирает или как оценивает, — новая версия, поэтому обратная связь на
одну версию не смешивается со следующей. `actions` — вызовы этого же API
(решить, открыть, взять в работу, поправить задачу, посмотреть прогоны,
отзыв); что из них показать и как — дело клиента.

### 2. Правила (версия 1)

| Правило | `kind` | `reasonCode` | Что выбирает | `score` |
|---|---|---|---|---|
| `approval.review` | `review` | `review_assigned` / `review_role` | pending **gate**-approval, который вызывающий вправе решить: работа стоит «на проверке» (ADR-0018, критерий `human` ADR-0067) | 80 + 1 за день ожидания (≤ 10) |
| `approval.decide` | `decision` | `decision_assigned` / `decision_role` | pending approval без gate, который вызывающий вправе решить | 70 + 1 за день ожидания (≤ 10) |
| `approval.undecidable` | `undecidable` | `undecidable_process_owner` / `undecidable_process_starter` / `undecidable_requester` | pending approval для роли, который никто не вправе решить: все держатели роли в его области исключены (разделение обязанностей, CP-ADR-0074 §7). Владельцу процесса, чей шаг его запросил (нет владельца — запустившему экземпляр), иначе — автору запроса (амендмент 2026-09-30) | 75 + 1 за день ожидания (≤ 10) |
| `task.due_not_started` | `deadline` | `due_soon` / `overdue` | задача вызывающего (исполнитель, иначе владелец) категории `backlog`/`active` со сроком ≤ now + 48 ч (включая просроченные), которую никто не начал: нет активного claim и не было ни одного run | просрочена — 90; иначе 60→80 по мере приближения срока |
| `task.blocked` | `blocked` | `task_blocked` | задача, где вызывающий — исполнитель или владелец, в статусе категории `blocked` | 55 |
| `task.delegated_failing` | `delegated_failure` | `runs_failed` | работа, которую вызывающий отдал другому (владелец, иначе автор; исполнитель — другой principal), категории `backlog`/`active`, последние ≥ 3 run подряд — `failed` | 65 + 5 за каждый провал сверх трёх (≤ 15) |

«Вправе решить» — ровно правило пригодности ADR-0018, прочитанное в обратную
сторону: approval адресован вызывающему, или требует роль, которую он держит
на весь tenant либо на workspace approval или его предка. Серия провалов
считается по попыткам задачи от последней: `running` её не рвёт и не
удлиняет, `succeeded`/`cancelled`/`suspended` обрывают. Заблокированная
работа попадает в `task.blocked`, а не в `task.delegated_failing`: первое
действие там — снять блокировку.

К `score` задачи (и approval задачи) прибавляется приоритет задачи:
`critical` +10, `high` +5, `medium` 0, `low` −5; итог в `0…100`.

### 3. «Моё» и видимость

Каждое правило само называет отношение вызывающего к объекту: адресат или
держатель роли approval, исполнитель, владелец или автор задачи. Это те же
отношения, из которых модель PDP выводит право чтения (`authz/catalog.yaml`:
`owner or requested_by or assignee`, пригодность approval), поэтому список не
показывает объект, который вызывающий не мог бы прочитать, и чужие объекты в
нём не появляются ни в каком режиме `authorize`. Отдельного фильтра по
`visible_objects` нет — он был бы шире правил, а не уже.

Исключение — `approval.undecidable` (амендмент 2026-09-30, CP-ADR-0074 §7):
владелец процесса не отношение approval в модели PDP, поэтому элемент
владельцу (или запустившему экземпляр) показывается, только если `authorize(approvals.read)` на этот
approval его пускает (в режиме `policy` — `approvals.read` на области
approval); автор запроса читает approval по отношению `requested_by`.

### 4. Обратная связь

`POST /api/v1/me/attention/{itemKey}:feedback` с телом
`{verdict: useful|not_needed, comment?}` (комментарий ≤ 1000 символов).
Элемент пересчитывается правилом, названным в ключе, только для вызывающего:
ключ, которого нет в его списке сейчас, — чужой объект, ушедший из списка,
неизвестное правило или испорченный ключ — `404 not_found` одинаково, ответ
не говорит, есть ли объект у кого-то ещё. Если правило не вычислилось,
`503 attention_rule_unavailable`: элемент может быть в списке.

Таблица `attention_feedback` — одна строка на `(tenant, principal, itemKey)`;
повторный вердикт заменяет прежний (`INSERT … ON CONFLICT DO UPDATE`: два
одновременных отзыва дают одну строку). В строке — правило и его версия,
`kind`, `reasonCode`, объект и `score` на момент отзыва: этого достаточно,
чтобы мерить точность версии правила. `201` — первый вердикт, `200` — замена;
`Idempotency-Key` поддерживается как у любой записи. Событие
`attention.feedback_recorded` (сущность `attention_feedback`, уровень tenant)
несёт вердикт и ссылку на правило и объект; текст комментария в журнал не
попадает (`hasComment`).

**Отзыв не меняет список.** «Не нужно было показывать» не прячет элемент:
pending approval, который человек счёл лишним, всё равно ждёт решения, и
ядро не делает вид, что его нет. Что правило выбирает, меняется только новой
версией правила — по накопленным отзывам. Клиент видит свой отзыв в поле
`feedback` элемента и может учесть его в показе.

### 5. Деградация

Правила вычисляются независимо, каждое в своём savepoint. Правило, которое
упало (`rule_failed`), для которого у credential нет права чтения
(`permission_missing`: `approvals.read` для правил approval, `tasks.read` для
правил задач) или для которого PDP недоступен (`policy_unavailable`),
попадает в `degraded[]`, остальные отвечают — ответ `200`. Правило, давшее
больше 100 элементов, отдаёт первые 100 и `truncated`. Без обоих прав запрос
— `403`.

### 6. Права

Новых прав нет. Чтение — `tasks.read` или `approvals.read` (каждое правило —
своё). Отзыв требует права чтения правила элемента и больше ничего: он
записывает только суждение вызывающего о своём же списке и не меняет ни
одного объекта ядра. Поэтому токен со scope `control-plane:read` может
оставить отзыв — осознанно.

### 7. Нейтральность

Правила читают только то, что ядро знает о любом домене: категории статусов,
плановые даты, адресацию approval, gate, роли, run. Ни ключей статусов, ни
полей пакета. Тест проходит одинаковый сценарий на двух доменах, поставленных
данными через публичный API: изменение кода (`software-change`) и оплата
счёта поставщика (`invoice-payment`).

## Последствия

- Харнесс (H006, H009) получает «Важное» одним запросом и живое обновление по
  событиям `approval.*`, `task.*`, `run.*` — перечитывая список.
- Список пересчитывается на каждый запрос: пять запросов в БД плюс по одному
  на роль вызывающего, ограниченной workspace. На ожидаемом объёме это дёшево;
  если станет дорого — индекс под `task.due_not_started` или материализация,
  отдельным решением.
- Правило «не начата» для людей, которые не берут claim, а двигают статус, —
  грубое: задача в `active`-статусе без claim и run считается не начатой.
  Уточнение (например, по признаку статуса «в работе» из типа) — новая версия
  правила.
- Отзывы копятся без использования в выдаче; как они влияют на правила —
  решение по данным, новой версией.
