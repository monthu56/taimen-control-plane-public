# TASK-000025: Реестр task_types и настраиваемый lifecycle work item — SPEC

Статус: completed; ветка `claude/task-000025-task-types-lifecycle`

Target: `control-plane`

Источник задачи: `TASK-000025` ([WI-1])

Источник решения: ADR-0015 «Модель work item», «Решение» п.1-2 и «Совместимость
и миграция»; ADR-0030 «Immutable project templates» и ADR-0031 «Project profile
and lifecycle» как прецедент.

## 1. Проблема и граница

Task в Control Plane не имеет типа, а её состояние прибито к перечислению в
схеме:

```sql
CHECK (status IN ('backlog','todo','in_progress','blocked','done','cancelled'))
```

Ядро принимает решения по **ключу** этого перечисления: `claims.py` отказывает
в claim при `status IN ('done','cancelled')` и переводит `todo|backlog` в
`in_progress`; `_claim_release.py` возвращает `in_progress` в `todo`;
`discovery.py` считает задачу доступной, если её статус не `done|cancelled`, а
предусловие выполненным, если оно `done`; `tasks.py` завершает задачу записью
литерала `done`.

Следствия ровно те, что зафиксировал ADR-0015. Вопрос, операция и инцидент не
имеют дома: 93 из 241 переносимой сущности ADR-0014 мигрируют как Task с
конвенцией в тексте. Состояния `review`, `answered`, `approved`,
`rolled_back` не выражаются вовсе — не потому, что их запрещает модель, а
потому, что перечисление в `CHECK` не открыто для расширения.

Для Workspace и Project это уже решено: `workspace_types` и
`project_templates` несут `field_schema` и `lifecycle_schema`, а профиль
проекта хранит **пару** «пользовательский ключ + системная категория», и ядро
ветвится только по категории (ADR-0031). Настоящая задача переносит этот же
приём на work item.

Граница задачи узкая и намеренно не совпадает с границей ADR-0015:

- в объёме — реестр типов, lifecycle, категория статуса и перевод решений ядра
  на категорию;
- **вне объёма** — `custom_fields` на задаче, плановые даты `start_date` /
  `due_date`, комментарии, метки, ранжирование, watchers, расширенная
  фильтрация (пункты 3, 4, 6, 7 ADR-0015). Пункт 5 уже выполнен в TASK-000026.

Тип без своего жизненного цикла — половина сущности, поэтому первые два пункта
решения ADR-0015 не разделяются и делаются здесь целиком.

## 2. Решение в одном абзаце

Ввести версионируемый реестр `task_types` по образцу `project_templates`;
добавить задаче обязательную ссылку на версию типа и вторую колонку
`system_status_category`; сделать `status` пользовательским ключом, объявленным
в `lifecycle_schema` типа, а все решения ядра — функцией категории. Каждому
тенанту создаётся системный тип `task` с текущими шестью статусами и полным
графом переходов между ними, поэтому существующие задачи, клиенты и события не
меняют поведения.

## 3. Реестр `task_types`

### 3.1 Форма

Таблица повторяет `project_templates` — это осознанное повторение, а не
случайное сходство: тот же инвариант («конфигурация, на которую ссылаются
живые сущности, не меняется под ними») требует того же механизма.

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | uuid | PK |
| `tenant_id` | uuid | владелец |
| `key` | text | стабильный идентификатор типа в тенанте |
| `version` | int | версия, выдаётся сервером |
| `display_name` | text | человекочитаемое имя |
| `description` | text | |
| `field_schema` | jsonb | JSON Schema для будущих `custom_fields` задачи |
| `lifecycle_schema` | jsonb | статусы и переходы (раздел 4) |
| `status` | text | `active` \| `deprecated` |
| `created_by`, `created_at`, `updated_at` | | |

Инварианты:

1. `UNIQUE (tenant_id, key, version)` — версия уникальна в пределах ключа.
2. `UNIQUE (tenant_id, id)` — цель для tenant-consistent FK из `tasks`.
3. Строка **иммутабельна после INSERT**; триггер БД
   `forbid_task_type_mutation` пропускает единственный переход
   `status: active -> deprecated`. Редактирование типа всегда означает
   «создать следующую версию».
4. `field_schema` и `lifecycle_schema` валидируются локально:
   `validate_json_schema_document` для первого, `parse_lifecycle` для второго.
   Внешние `$ref` запрещены существующей проверкой `_reject_remote_refs` —
   хранимая схема не должна превращаться в SSRF-примитив и в зависимость от
   чужого аптайма.

`field_schema` вводится здесь пустым и **не применяется ни к чему** до WI-3:
поля задачи в объёме этой задачи нет. Колонка заводится сразу, потому что
добавить её потом означало бы вторую миграцию по той же таблице ради одного
`jsonb`, а версионируемый реестр без схемы полей — заведомо неполный контракт.

### 3.2 Почему нет колонки `is_system`

`workspace_types` помечает системный fallback булевым полем и частичным
уникальным индексом `WHERE is_system`. Для версионируемой таблицы этот
инвариант не выражается: индекс по `(tenant_id)` запретит вторую версию
системного типа, а индекс по `(tenant_id, version)` не запретит второй
системный **ключ**.

Поэтому системный тип опознаётся константой ключа
`SYSTEM_TASK_TYPE_KEY = "task"`, а защита от «сломать себе тенант» приходит не
из флага, а из иммутабельности версий: создание версии 2 ключа `task` не
трогает ни одной существующей задачи — они ссылаются на конкретную версию по
`type_id`. Это то же свойство, на котором стоит ADR-0030.

### 3.3 Deprecate, а не delete

Удаления типа нет, как нет его у шаблона проекта. `:deprecate` убирает версию
из выдачи «последняя активная» и не влияет ни на одну задачу, которая на неё
ссылается. Задача, чей тип deprecated, продолжает жить и менять статус: тип —
это конфигурация, к которой задача уже привязана, а не действующее разрешение.

## 4. `lifecycle_schema` work item

### 4.1 Категории

```text
backlog             не готова к взятию (организационно, а не технически)
active              в работе или готова к взятию
blocked             ожидает внешнего условия
terminal_success    завершена успешно
terminal_cancelled  закрыта без результата
```

Это **другой** словарь, чем у проекта (`planned`/`active`/`paused`/
`terminal_success`/`terminal_cancelled`). Общими остаются машинерия разбора
(`parse_lifecycle`), дата-класс `Lifecycle` и обе терминальные категории;
допустимый набор категорий становится параметром разбора. Слить словари в один
было бы ошибкой: «паузa проекта» и «блокировка задачи» — разные вещи, и
единственный общий словарь начал бы обслуживать оба смысла плохо.

### 4.2 Документ

```json
{
  "initialStatus": "todo",
  "statuses": [
    {"key": "backlog", "displayName": "Backlog", "category": "backlog"},
    {"key": "todo", "displayName": "To do", "category": "active"},
    {"key": "in_progress", "displayName": "In progress", "category": "active"},
    {"key": "blocked", "displayName": "Blocked", "category": "blocked"},
    {"key": "done", "displayName": "Done", "category": "terminal_success"},
    {"key": "cancelled", "displayName": "Cancelled", "category": "terminal_cancelled"}
  ],
  "transitions": [
    {"from": "backlog", "to": ["todo", "in_progress", "blocked", "done", "cancelled"]},
    {"from": "todo", "to": ["backlog", "in_progress", "blocked", "done", "cancelled"]},
    {"from": "in_progress", "to": ["backlog", "todo", "blocked", "done", "cancelled"]},
    {"from": "blocked", "to": ["backlog", "todo", "in_progress", "done", "cancelled"]}
  ],
  "claimStatus": "in_progress",
  "releaseStatus": "todo",
  "completionStatus": "done"
}
```

`statuses`, `initialStatus` и `transitions` разбираются тем же кодом, что и у
проекта, с теми же ограничениями (не более 100 статусов, ключ до 64 символов,
запрет дубликатов и ссылок на необъявленные статусы).

### 4.3 Три служебных ключа

Ядро совершает три автоматических перехода, которые сегодня зашиты литералами.
Чтобы перевести их на конфигурацию, а не на угадывание по категории, lifecycle
объявляет их явно:

| Ключ | Когда применяется | Сегодняшний литерал |
|---|---|---|
| `claimStatus` | задача взята в claim | `in_progress` |
| `releaseStatus` | claim снят, задача не завершена | `todo` |
| `completionStatus` | `POST /tasks/{ref}:complete` | `done` |

Правила валидации при создании версии типа:

- каждый из трёх, если указан, должен называть объявленный статус;
- `claimStatus` и `releaseStatus` не могут быть терминальными: claim не
  завершает задачу, а снятие claim не отменяет её;
- `completionStatus` обязан иметь категорию `terminal_success`. Если он не
  указан, он выводится: единственный статус категории `terminal_success`. Если
  таких статусов несколько и `completionStatus` не объявлен — отказ
  `invalid_lifecycle_schema` при создании типа, а не догадка при завершении
  задачи. Если статусов категории `terminal_success` нет вовсе, тип нельзя
  завершить через `:complete`, и это тоже отказ при создании: work item, у
  которого нет успешного финала, не описывает работу.

### 4.4 Автоматический переход применяется только по объявленному ребру

`claimStatus` и `releaseStatus` применяются **только если ребро из текущего
статуса объявлено**. Иначе статус остаётся прежним, а операция (claim или
release) выполняется.

Это единственное место, где «переход только по объявленному ребру» не
превращается в отказ, и причина в приоритетах: авторитетным механизмом
координации является claim с lease и fencing, а не подпись под ним. Отказать в
claim из-за того, что тенант не объявил ребро `blocked -> in_progress`,
означало бы превратить косметику конфигурации в отказ в обслуживании. Обратное
поведение — молча переводить задачу по необъявленному ребру — нарушило бы
инвариант lifecycle. Остаётся третье: выполнить операцию, статус не трогать.

`completionStatus` — не автоматический переход, а результат явного действия
пользователя, поэтому он проверяется строго: ребро `текущий ->
completionStatus` обязано быть объявлено, иначе `:complete` отказывает
(раздел 6.4).

## 5. Задача: тип и пара статусов

### 5.1 Колонки

```text
tasks.type_id                 uuid NOT NULL  -> task_types(id), tenant-consistent FK
tasks.status                  text NOT NULL  -- пользовательский ключ
tasks.system_status_category  text NOT NULL  -- одна из пяти категорий
```

Старый `CHECK (status IN (...))` снимается, вместо него:

- `CHECK (char_length(status) BETWEEN 1 AND 64)` — тот же предел, что у ключа
  статуса в lifecycle;
- `CHECK (system_status_category IN ('backlog','active','blocked',
  'terminal_success','terminal_cancelled'))`.

БД больше не знает, какие ключи допустимы: это знание живёт в
`lifecycle_schema` типа и проверяется приложением под блокировкой строки —
ровно так же, как у профиля проекта. Ослабления инварианта здесь нет, есть
перенос: перечисление шести значений в схеме никогда не проверяло
**соответствие** статуса типу, потому что типа не было.

Индекс `ix_tasks_tenant_status` сохраняется (фильтрация по ключу остаётся) и
дополняется `ix_tasks_tenant_category` по `(tenant_id,
system_status_category)`: по нему ходит discovery, и это горячий путь.

### 5.2 Пара всегда согласована

`system_status_category` никогда не приходит от клиента. Она вычисляется из
`lifecycle_schema` типа задачи в момент любой записи статуса и в момент
создания задачи. Клиент, отправивший `systemStatusCategory` в теле, получает
её проигнорированной — поле не объявлено в request-схемах.

Единственный способ рассогласовать пару — сменить тип задачи под ней. Поэтому
**смена типа задачи в этой задаче не вводится**: `PATCH /tasks/{ref}` не
принимает `typeId`. Тип задаётся при создании и дальше неизменен. Ретайп —
отдельное решение: он требует отображения статусов старого lifecycle в новый,
а это ровно тот класс операции, который нельзя выполнять по умолчанию.

## 6. Поведение ядра

Ниже — полный список мест, где сегодня стоит литерал статуса, и во что он
превращается. Категория обозначена через `cat(task)`.

### 6.1 Claimability

| Сегодня | Становится |
|---|---|
| `status IN ('done','cancelled')` → `task_not_claimable` | `cat(task) ∈ {terminal_success, terminal_cancelled}` → тот же код |
| `status IN ('todo','backlog')` → `in_progress` | применить `claimStatus`, если ребро объявлено (4.4) |

`blocked` остаётся **claimable ровно как сегодня**. Категория `blocked`
описывает ожидание внешнего условия, а не запрет на взятие; сегодняшний код
не запрещает claim заблокированной задачи, и настоящая задача не меняет
поведения на существующих данных. Запрет claim по категории `blocked` — это
отдельное продуктовое решение с собственной миграцией ожиданий, и оно не
делается здесь походя.

Организационная eligibility, готовность по зависимостям и approval gate не
затрагиваются.

### 6.2 Снятие claim

`release_claim_on_locked_task` сегодня: `if status == 'in_progress': status =
'todo'`. Становится: если текущий статус равен `claimStatus` типа и ребро
`claimStatus -> releaseStatus` объявлено, перевести в `releaseStatus`.

Условие «текущий статус равен `claimStatus`» — прямой аналог сегодняшнего
`== 'in_progress'`: снятие claim не должно вытаскивать задачу из статуса,
который поставил человек вручную.

Функция синхронная и не имеет доступа к типу, поэтому lifecycle передаётся
параметром: вызывающие уже держат блокировку строки задачи и загружают тип.

### 6.3 Готовность зависимостей

`check_task_readiness` и запрос discovery считают предусловие выполненным по
`status != 'done'`. Становится `system_status_category != 'terminal_success'`.

Отменённое предусловие продолжает блокировать — задокументированное поведение
ADR-0011 сохраняется дословно, теперь уже по категории.

### 6.4 Завершение

`verify_task_completable`:

| Сегодня | Становится | Код ответа |
|---|---|---|
| `status == 'done'` | `cat(task) == terminal_success` | `409 task_already_completed` |
| `status == 'cancelled'` | `cat(task) == terminal_cancelled` | `422 task_cancelled` |

`finish_locked_task` пишет `completionStatus` типа вместо литерала `done` и
проставляет категорию `terminal_success`. Если ребро `текущий ->
completionStatus` не объявлено — `422 invalid_transition` с перечислением
допустимых целей. Задача при этом не меняется, версия не растёт.

### 6.5 Создание задачи

Сегодня: `status` обязан быть `backlog` или `todo`.

Становится: по умолчанию `initialStatus` типа; явный статус допускается, если
он объявлен и его категория — `backlog`, **либо** он равен `initialStatus`.

Для системного типа это ровно `{backlog, todo}` — сегодняшнее правило без
изменений. Более широкое правило («любой нетерминальный») было отвергнуто:
оно позволило бы создать задачу сразу в `in_progress` без claim, то есть
записать в авторитетное состояние заведомую неправду.

`typeKey` (и опционально `typeVersion`) принимается при создании; без него
берётся последняя активная версия системного типа. Тип, у которого нет ни
одной активной версии, — `404`.

### 6.6 Смена статуса через `PATCH`

Сегодня: любой из пяти статусов (кроме `done`) из любого статуса, без проверки
рёбер; `done` отклоняется с подсказкой про `:complete`.

Становится, под `If-Match` и claim-gate (оба сохраняются без изменений):

1. целевой статус обязан быть объявлен в lifecycle типа — иначе
   `422 status_not_in_lifecycle` с перечислением известных ключей;
2. категория `terminal_success` отклоняется с сегодняшним сообщением про
   `:complete` — завершение остаётся отдельным действием, потому что оно
   снимает claim, разбирается с running run и пишет `completed_at`;
3. переход обязан быть объявлен ребром — иначе `422 invalid_transition` с
   `details.from`, `details.to`, `details.allowed`;
4. смена на текущий статус — `422 invalid_transition` (как у проекта).

Пункты 3 и 4 — единственное сужение поведения относительно сегодняшнего. Для
существующих задач оно ненаблюдаемо: граф системного типа полон на четырёх
нетерминальных статусах и содержит рёбра в оба терминальных, то есть
разрешает всё, что разрешено сегодня, кроме перехода в самого себя. Переход
«в тот же статус» сегодня проходит и увеличивает версию; после изменения он
отклоняется. Это осознанная унификация с моделью проекта, и она вынесена в
раздел 9 как единственное breaking-изменение контракта.

### 6.7 Фильтрация списка

`GET /tasks?status=` сегодня валидируется по глобальному перечислению.
Глобального перечисления больше нет, поэтому:

- `status` фильтрует по ключу как есть, валидация — только длина. Неизвестный
  ключ даёт пустую страницу, а не `422`: ключ, известный одному типу, не
  обязан быть известен другому, и «валидный» здесь не определён глобально;
- добавляется `systemStatusCategory` — фильтр по категории, валидируемый по
  словарю из пяти значений;
- добавляется `typeKey` — фильтр по ключу типа.

Расширенная фильтрация ADR-0015 (owner, даты) остаётся вне объёма; эти три
фильтра вводятся потому, что без них категорию невозможно наблюдать через API,
а значит невозможно проверить.

## 7. HTTP API (`/api/v1`)

### 7.1 Реестр

| Метод и путь | Право | Ответ |
|---|---|---|
| `POST /task-types` | `task_types.manage` | `201 TaskTypeOut` |
| `GET /task-types` | `task_types.read` | страница; `?key=` сужает, по умолчанию только последние активные версии |
| `GET /task-types/{id}` | `task_types.read` | `TaskTypeOut` |
| `POST /task-types/{id}:deprecate` | `task_types.manage` | `200 TaskTypeOut`, идемпотентно |

Права новые и отдельные от `tasks.*`: право менять словарь состояний тенанта
не следует из права заводить задачи. `ADMIN` покрывает оба, как и везде.

`POST /task-types` создаёт **следующую версию** ключа; клиент версию не
задаёт. Аллокация версии сериализуется тем же advisory-локом на
`(tenant, key)`, что и у шаблонов проекта.

### 7.2 Задача

`TaskOut` дополняется: `typeId`, `typeKey`, `typeVersion`,
`systemStatusCategory`. Поле `status` **остаётся ключом статуса** и стоит на
том же месте — это и есть условие совместимости из ADR-0015: категория
добавляется рядом, а не вместо.

`TaskCreateRequest` дополняется необязательными `typeKey` и `typeVersion`.
`TaskUpdateRequest` не меняется.

`typeKey` и `typeVersion` в `TaskOut` — денормализация: они читаются из типа
и позволяют клиенту не делать второй запрос ради имени статуса. Строится тем
же приёмом, что и `projectId` в `task_bodies` — один запрос на страницу, а не
на строку.

## 8. События

| Событие | Изменение payload |
|---|---|
| `task.created` | добавляются `typeKey`, `typeVersion`, `systemStatusCategory` |
| `task.updated` | при смене статуса в `changes` появляется `systemStatusCategory`; добавляется `fromStatus` |
| `task.claimed` | добавляется `systemStatusCategory` |
| `task.completed` | добавляются `status` (ключ завершения) и `systemStatusCategory` |
| `claim.released` | `taskStatus` остаётся ключом, добавляется `taskSystemStatusCategory` |
| `task_type.created`, `task_type.deprecated` | новые, `entity_type = "task_type"` |

Существующие поля не переименовываются и не меняют смысл: подписчик, который
читает `status`, продолжает читать ключ.

## 9. Совместимость

1. **Схема.** `type_id` и `system_status_category` добавляются как nullable,
   заполняются, затем становятся `NOT NULL`. Старый `CHECK` снимается после
   заполнения.
2. **Данные.** Каждому тенанту создаётся системный тип `task` версии 1 с
   шестью статусами и полным графом рёбер. Каждая существующая задача получает
   `type_id` этого типа и категорию по отображению
   `backlog→backlog`, `todo→active`, `in_progress→active`, `blocked→blocked`,
   `done→terminal_success`, `cancelled→terminal_cancelled`. Статусы не
   меняются.
3. **Claimability не меняется.** До миграции claimable = статус не `done` и не
   `cancelled`; после — категория не терминальная. На отображении выше это
   одно и то же множество задач.
4. **API.** `status` остаётся ключом во всех ответах и запросах. Новые поля
   только добавляются. Единственное сужение — отказ на переход «в тот же
   статус» (6.6).
5. **Новые тенанты.** `bootstrap` создаёт системный тип так же, как создаёт
   системный workspace type.

### Downgrade

Downgrade возвращает шестизначный `CHECK`, поэтому обязан привести данные к
нему. Статусы, которых в нём нет (введённые тенантом после апгрейда),
отображаются по категории: `backlog→backlog`, `active→todo`,
`blocked→blocked`, `terminal_success→done`, `terminal_cancelled→cancelled`.

Это **потеря пользовательских ключей** и она необратима. Альтернативы нет:
шестизначный `CHECK` не примет `review`. Downgrade документирован как
аварийный, а не как штатный откат; сообщение об этом стоит в docstring
ревизии.

## 10. Threat и failure model

Полностью — в `docs/verification/TASK-000025-threat-model.md`. Здесь список
того, что защита обязана покрыть:

- `lifecycle_schema` и `field_schema` — attacker-influenced JSON: размер,
  глубина, количество узлов ограничиваются **до** передачи в движок схем;
  внешние `$ref` запрещены;
- статус, объявленный в чужом тенанте, не применим: тип резолвится с фильтром
  по `tenant_id`, задача — тоже;
- конкурентные переходы: две одновременные смены статуса под `If-Match`
  сериализуются блокировкой строки задачи; проигравший получает `409
  version_conflict` и не меняет ни статус, ни версию;
- гонка «claim против перехода в терминальный статус» разрешается тем же
  порядком блокировок (задача, затем claim), что и сегодня;
- deprecate типа не может обездвижить задачи, которые на него ссылаются;
- иммутабельность версии типа обеспечивается триггером БД, а не только
  приложением.

## 11. Verification

Матрица — в `docs/verification/TASK-000025-verification.md`. Acceptance задачи
закрывается пунктами:

1. задача не принимает статус, не объявленный в lifecycle своего типа;
2. переход по необъявленному ребру отклоняется и **не меняет версию**;
3. claimability и завершение считаются по категории, а не по ключу;
4. `lifecycle_schema` валидируется локально, внешние `$ref` не резолвятся и не
   порождают сетевых обращений;
5. миграция `upgrade → downgrade → upgrade` проходит;
6. существующие задачи сохраняют статусы и остаются claimable;
7. `status` остаётся в API ключом, категория добавлена рядом;
8. tenant isolation и конкурентные переходы закреплены тестами;
9. полный gate: `ruff`, `mypy`, `pytest`.

## 12. Out of scope

- `custom_fields` задачи и применение `field_schema` (WI-3);
- `start_date` / `due_date` (WI-3);
- комментарии (WI-4, TASK-000028);
- метки, ранжирование, watchers, полнотекстовый поиск (границы ADR-0015);
- смена типа существующей задачи (ретайп) — раздел 5.2;
- запрет claim по категории `blocked` — раздел 6.1;
- MCP-инструменты управления реестром типов: расширение MCP-поверхности
  требует отдельного решения по governance, а чтение типа задачи попадает в
  `cp_get_task` через `TaskOut` без новых инструментов.
