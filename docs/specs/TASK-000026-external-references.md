# TASK-000026: Обобщение external references на work item — SPEC

Статус: completed; ветка `claude/task-000026-external-references`

Target: `control-plane`

Источник задачи: `TASK-000026` ([WI-2])

Источник решения: ADR-0015 «Модель work item», «Решение» п.5; ADR-0034
«Generic external references как mapping, а не источник истины»

## 1. Проблема и граница

Таблица `external_references` спроектирована product-neutral и уже generic:
идентичность внутренней стороны выражена парой `entity_type` + `entity_id`,
уникальность внешней стороны — `UNIQUE (tenant_id, external_system,
external_type, external_id)` (ADR-0034). Generic только хранилище. Всё, что
выше него, знает ровно один тип сущности:

- HTTP-доступ существует только как под-ресурс проекта —
  `GET|POST /projects/{id}/external-references`;
- команда `add_external_reference` принимает `project_id`, вызывает
  `require(ctx, Permission.PROJECTS_MANAGE)` и `get_tenant_project`, а затем
  записывает литерал `entity_type="project"`;
- обратный поиск существует только как фильтр `GET /projects?externalSystem=…`.

Следствие видно в соседнем решении: ADR-0014 не может сохранить legacy-
идентификаторы перенесённых задач как записи и вынужденно вводит текстовую
конвенцию в описании задачи:

```text
SYM-MIG-REF: system=external-root; type=task; id=SYM-T-070
```

Конвенция в свободном тексте — это индекс, которого нет: дедупликация импорта
опирается на подстроку, обратное отображение требует парсинга описания, а
уникальность внешнего ключа не гарантируется ничем.

Граница остаётся границей ADR-0034 и не расширяется: external reference — это
**отображение**, а не источник истины. Control Plane не пишет во внешнюю
систему, не считает её состояние авторитетным и не синхронизирует ничего по
этой записи. Меняется только то, **на какие внутренние сущности** отображение
разрешено и **кто** имеет право его установить.

## 2. Решение в одном абзаце

Ввести явный реестр **entity bindings**: `entity_type` → (загрузчик сущности в
пределах тенанта, permission на чтение, permission на управление). Обобщённая
команда и обобщённые HTTP-эндпоинты работают через реестр, а не через проект.
Проектный скоуп сохраняется как частный случай того же кода и того же
контракта. В реестре v0.8 два типа: `project` и `task`.

## 3. Почему реестр, а не свободный `entity_type`

Колонка `entity_type` — свободный текст, и соблазн принять её значение от
клиента как есть велик. Это была бы дыра, а не обобщение:

- **обход авторизации.** Право на запись выводится из типа сущности. Клиент,
  который может объявить `entity_type` сам, объявляет тип, для которого
  проверки нет, и получает право писать в общий namespace внешних ключей;
- **захват внешнего ключа.** Уникальность `(tenant, system, type, external_id)`
  глобальна в пределах тенанта. Запись на несуществующий тип занимает ключ и
  делает последующую честную регистрацию невозможной — отказ в обслуживании на
  уровне импорта;
- **неразрешимые ссылки.** `entity_id` без известного типа некуда резолвить:
  ни проверить принадлежность тенанту, ни показать в UI, ни удалить вместе с
  сущностью.

Поэтому неизвестный `entityType` — `422 invalid_entity_type` с перечислением
поддерживаемых типов в `details.supported`. Список типов расширяется кодом
(WI-1 добавит типы work item поверх того же реестра), а не запросом.

## 4. Реестр entity bindings

| `entityType` | Загрузчик (в пределах тенанта) | Чтение | Управление |
|---|---|---|---|
| `project` | `ProjectProfile` по UUID | `projects.read` | `projects.manage` |
| `task` | `Task` по UUID **или** public id (`TASK-000026`) | `tasks.read` | `tasks.write` |

Инварианты реестра:

1. **Право определяется типом целевой сущности, а не проектом.** Регистрация
   ссылки на задачу требует `tasks.write` и не требует `projects.manage`.
   Harness-ключ, которому выданы права на задачи, может зарегистрировать
   legacy-идентификатор задачи, не получая права переписывать проект.
2. **Загрузчик всегда фильтрует по `ctx.tenant_id`.** Существование сущности и
   принадлежность тенанту — одна проверка, а не две; чужой UUID неотличим от
   несуществующего.
3. **Хранится всегда UUID.** `entityId` в запросе — ссылка (`entityRef`),
   которую резолвит загрузчик типа; в колонку `entity_id` пишется
   разрешённый UUID. Public id задачи принимается на входе именно потому, что
   импортёр из ADR-0014 оперирует ими.

## 5. Идемпотентность и конфликт

Семантика ADR-0034 сохраняется дословно и распространяется на все типы.
Решение принимается по внешнему ключу `(tenant, external_system,
external_type, external_id)`, строка которого блокируется `SELECT … FOR UPDATE`:

| Состояние | Результат |
|---|---|
| ключа нет | `201`, запись создана, событие `<entityType>.external_reference_added` |
| ключ есть, та же сущность, то же `metadata` | `200`, **ничего не записано**, `version` не меняется, события нет |
| ключ есть, та же сущность, другое `metadata` | `200`, обновлено только `metadata`, `version += 1`, событие `<entityType>.external_reference_updated` |
| ключ есть, другая сущность (любого типа) | `409 external_reference_conflict`, `details.entityType` / `details.entityId` |

Повтор с тем же телом не создаёт дубликат и не двигает версию — это и есть
дедупликация повторного импорта, ради которой ADR-0014 вводил текстовую
конвенцию.

Проверка «та же сущность» сравнивает **пару** `(entity_type, entity_id)`.
Совпадение UUID при разном типе — конфликт: UUID разных таблиц не образуют
общего пространства имён, и молчаливое переиспользование ключа было бы худшим
из возможных ответов.

Гонка двух одновременных регистраций одного ключа разрешается уникальным
индексом: проигравший получает `409`, а не мёртвую транзакцию — вставка идёт
внутри `SAVEPOINT` (поведение существующего кода сохраняется).

Идентичность записи неизменяема на уровне БД: триггер
`forbid_external_reference_identity_change` запрещает UPDATE `entity_type`,
`entity_id` и всех трёх внешних полей. Обобщение не ослабляет триггер и не
требует миграции схемы — таблица уже generic.

## 6. HTTP API (`/api/v1`)

### `POST /external-references`

Требует permission **управления** того типа, который указан в теле.

```json
{
  "entityType": "task",
  "entityId": "TASK-000026",
  "externalSystem": "external-root",
  "externalType": "task",
  "externalId": "SYM-T-070",
  "metadata": {"sourcePath": "operations/tasks/SYM-T-070.md"}
}
```

Ответ — `ExternalReferenceOut` (без изменений формы): `201` при создании,
`200` при попадании в существующий ключ. `Idempotency-Key` работает как на
остальных write-эндпоинтах.

### `GET /external-references`

Два взаимоисключающих режима, оба всегда в пределах тенанта вызывающего.

1. **Прямой** — `?entityType=&entityId=` — ссылки одной сущности, страницами.
   Требует permission **чтения** этого типа.
2. **Обратный** — `?externalSystem=&externalType=&externalId=` — по внешнему
   ключу к внутренней сущности. `externalSystem` и `externalId` обязательны
   вместе; `externalType` опционален и сужает выборку.

Смешение режимов и полузаданный обратный поиск — `422
invalid_external_lookup`. Причина та же, по которой она уже существует для
проектов: полузаданный фильтр молча вырождается в «отдай всё».

### Обратный поиск и enumeration

Обратный режим отвечает на вопрос «какой внутренней сущности принадлежит этот
внешний ключ», то есть раскрывает `entityType` + `entityId`. Поэтому после
резолва ссылки проверяется permission **чтения найденного типа**, и при его
отсутствии ответ — пустая страница, а не `403`.

Различать «ключа нет» и «ключ есть, но не для тебя» означало бы отдать oracle
по внешним идентификаторам: перебором чужих тикетов можно было бы установить,
какие из них заведены в тенанте. Это тот же принцип единого ответа, что и в
scoped tool discovery (ADR-0045).

### Совместимость: проектный скоуп

`GET|POST /projects/{id}/external-references` и фильтр
`GET /projects?externalSystem=&externalType=&externalId=` **сохраняются без
изменения контракта**: те же пути, те же permissions, те же коды ответов, те
же события. Реализация становится тонкой делегацией в обобщённую команду с
`entity_type="project"`; отдельной ветки логики для проектов не остаётся —
иначе через год они разойдутся.

## 7. События

Тип события выводится из типа сущности: `<entityType>.external_reference_added`
и `<entityType>.external_reference_updated`. Для проекта это **ровно** сегодняшние
`project.external_reference_added|updated` — существующие подписчики не
затрагиваются. Для задачи появляется `task.external_reference_*`.

`entity_type` / `entity_id` строки события указывают на целевую сущность,
поэтому событие попадает в тот же поток, что и остальная история этой
сущности, и подписчику не нужно знать про отдельный тип «ссылка».

Payload не расширяется полями сверх существующих (`externalReferenceId`,
`externalSystem`, `externalType`, `externalId`). `metadata` в событие не
попадает: это документ, границы и содержимое которого задаёт клиент, а поток
событий доставляется шире, чем сама запись.

## 8. Границы данных и secret scan

Сохраняются без ослабления и применяются одинаково ко всем типам:

- `externalSystem`, `externalType`, `externalId` — 1..512 символов каждый;
- `metadata` сначала ограничивается по размеру и глубине
  (`guard_json_document`), и только потом обходится рекурсивным детектором
  secret material (`validate_config_document`). Порядок принципиален: скан
  рекурсивен, и документ нужно ограничить **до** обхода;
- находка secret material — отказ записи, а не редактирование.

## 9. Failure model

| Сценарий | Ответ |
|---|---|
| неизвестный `entityType` | `422 invalid_entity_type`, `details.supported` |
| сущность чужого тенанта или несуществующая | `404` того же вида, что и «нет такой» |
| нет permission управления для типа | `403 forbidden`, `details.required` |
| та же регистрация повторно | `200`, без новой строки и без роста версии |
| ключ занят другой сущностью | `409 external_reference_conflict` |
| гонка двух создателей одного ключа | один `201`, второй `409`; транзакция жива |
| попытка сменить идентичность записи | отказ триггера БД |
| обратный поиск ключа, тип которого недоступен по чтению | пустая страница |
| полузаданный обратный поиск | `422 invalid_external_lookup` |
| секрет в `metadata` | отказ записи |

## 10. Что закрывается в ADR-0014

Конвенция `SYM-MIG-REF` в тексте описания заменяется записью:

```json
{"entityType": "task", "entityId": "TASK-000026",
 "externalSystem": "external-root", "externalType": "task",
 "externalId": "SYM-T-070"}
```

Миграции данных нет: перенесённых задач с этой конвенцией на момент задачи не
существует, импорт ADR-0014 ещё не выполнялся. ADR-0014 обновляется как
документ — конвенция в описании перестаёт быть решением и становится
историческим обходным путём.

## 11. Out of scope

- типы work item, `custom_fields`, lifecycle (WI-1, WI-3) — реестр bindings
  расширяется ими позже и специально сделан открытым к расширению;
- массовый импорт и bulk-регистрация;
- удаление external reference через API — ограничение v0.5 (ADR-0034)
  сохраняется как есть;
- запись во внешнюю систему, синхронизация и любое чтение её состояния;
- MCP-инструмент для регистрации ссылок: у импортёра ADR-0014 есть SDK,
  а расширение MCP-поверхности требует отдельного решения по governance.

## 12. Acceptance и verification

1. Повторная регистрация того же external reference идемпотентна: дубликат не
   создаётся, `version` не растёт, лишнего события нет.
2. External reference не пересекает границу тенанта ни при записи, ни при
   прямом, ни при обратном поиске.
3. Привязка к несуществующей или чужой сущности отклоняется; неизвестный
   `entityType` отклоняется до любой записи.
4. Право проверяется по типу целевой сущности: `tasks.write` достаточно для
   задачи и недостаточно для проекта, `projects.manage` — наоборот.
5. Проектные эндпоинты и фильтр `GET /projects?external…` работают без
   изменения контракта, включая коды `200`/`201`/`409` и типы событий.
6. Конвенция `SYM-MIG-REF` выражается записями; миграция данных не требуется.
7. Secret scan `metadata` сохраняется для всех типов сущностей.
8. Полный gate: тесты, lint, типы; миграция upgrade/downgrade/upgrade без
   изменений схемы.
