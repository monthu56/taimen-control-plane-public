# TASK-000025: Реестр task_types и lifecycle work item — threat/failure model

Статус: completed

Связанные документы: `docs/specs/TASK-000025-task-types-lifecycle.md`,
`docs/plans/TASK-000025-task-types-lifecycle.md`,
`docs/adr/0048-work-item-type-and-lifecycle.md`.

## 1. Активы

| Актив | Почему ценен |
|---|---|
| Словарь состояний тенанта (`lifecycle_schema`) | определяет, что ядро считает завершённым, заблокированным и доступным к взятию |
| Пара `status` + `system_status_category` задачи | единственный вход claimability, готовности зависимостей и завершения |
| Иммутабельность версии типа | живые задачи ссылаются на конкретную версию; правка под ними меняет смысл уже принятых решений |
| Горячий путь claim/complete | координация исполнителей; отказ здесь останавливает работу, а не украшение |
| `field_schema` и `lifecycle_schema` как хранимый JSON | attacker-influenced документ, который попадает в движок схем |
| Версия задачи (`If-Match`) | основа оптимистичной блокировки; ложный рост версии ломает клиентов |

## 2. Модель нарушителя

- **A1. Принципал с `tasks.write`**: заводит и двигает задачи; не должен уметь
  переопределять словарь состояний тенанта.
- **A2. Принципал с `task_types.manage`**: легитимно настраивает процесс; может
  по ошибке или намеренно объявить lifecycle, который ломает ядро (нет
  успешного финала, терминальный `claimStatus`, самопетля).
- **A3. Принципал другого тенанта**: хочет применить свой тип или свой статус к
  чужой задаче.
- **A4. Автор схемы**: кладёт в `field_schema`/`lifecycle_schema` документ,
  который дорог или опасен для валидатора (глубокая вложенность, внешний
  `$ref`).
- **A5. Конкурирующий клиент**: две сессии двигают одну задачу одновременно и
  рассчитывают на `If-Match`.
- **A6. Prompt injection в тексте задачи**: заставляет агента объявить статус
  «завершено» вместо реального завершения.

## 3. Угрозы и контроли

| # | Угроза | Вектор | Контроль | Проверка |
|---|---|---|---|---|
| T1 | Присвоение задаче статуса, которого нет в её lifecycle | A1 отправляет `status: "review"` типу без такого статуса | целевой статус ищется в `lifecycle_schema` типа задачи под блокировкой строки → `422 status_not_in_lifecycle` | `test_status_outside_the_lifecycle_is_rejected` |
| T2 | Обход процесса переходом по необъявленному ребру | A1 двигает `backlog → done` в типе, где такого ребра нет | `lifecycle.allows(from, to)` → `422 invalid_transition`; **версия и статус не меняются** | `test_undeclared_transition_changes_neither_status_nor_version` |
| T3 | Ложное завершение задачи | A6 добивается `PATCH status=<терминальный>` вместо `:complete` | категория `terminal_success` недоступна через `PATCH`; завершение только через `:complete`, который снимает claim, разбирается с running run и пишет `completed_at` | `test_patch_cannot_reach_terminal_success` |
| T4 | Решение ядра по имени статуса вместо смысла | тенант заводит ключ `done` категории `active` (или `archived` категории `terminal_success`) | claimability, готовность и завершение читают только `system_status_category`; в `src/` не остаётся сравнений `Task.status` с литералом | `test_core_decisions_follow_the_category_not_the_key` |
| T5 | Кросс-тенантное применение типа | A3 подставляет `typeId` чужого тенанта | резолв типа фильтрует по `tenant_id`; чужое неотличимо от отсутствующего (`404`) | `test_task_type_does_not_cross_the_tenant_boundary` |
| T6 | Правка lifecycle под живыми задачами | A2 меняет `lifecycle_schema` существующей версии | версия иммутабельна: триггер `forbid_task_type_mutation` пропускает только `active → deprecated`; правка — это новая версия, на которую старые задачи не ссылаются | `test_version_content_is_immutable_even_against_raw_sql` |
| T7 | Lifecycle, который делает задачи незавершаемыми | A2 объявляет тип без статуса категории `terminal_success` | отказ **при создании типа**, а не при попытке завершить задачу | `test_lifecycle_without_success_is_refused` |
| T8 | Lifecycle, который завершает задачу самим фактом claim | A2 объявляет терминальный `claimStatus` | `claimStatus`/`releaseStatus` обязаны быть нетерминальными | `test_service_status_must_not_be_terminal` |
| T9 | Неоднозначное завершение | A2 объявляет два статуса `terminal_success` без `completionStatus` | отказ при создании типа: угадывать финал нельзя | `test_ambiguous_completion_status_is_refused` |
| T10 | SSRF и зависимость от чужого аптайма через `$ref` | A4 кладёт абсолютный `$ref` в схему | `_reject_remote_refs`: разрешён только same-document `#`; сетевых обращений нет | `test_remote_ref_in_field_schema_is_refused` |
| T11 | CPU-затраты на валидации | A4 кладёт глубокий/огромный документ | `guard_json_document` (64 KiB, 20 уровней, 5000 узлов) **до** движка схем; не более 100 статусов | `test_pathological_nesting_is_refused`, `test_too_many_statuses_are_refused` |
| T12 | Потерянное обновление при конкурентных переходах | A5 двигает задачу из двух сессий | `If-Match` + `SELECT … FOR UPDATE` на строке задачи: ровно один `200`, второй `409 version_conflict` | `test_concurrent_transitions_produce_one_winner` |
| T13 | Захват задачи в терминальной категории | A5 гоняет claim против завершения | тот же порядок блокировок (задача → claim), что и сегодня; claim в терминальной категории отказывает | `test_claim_races_completion` |
| T14 | Обездвиживание задач через deprecate типа | A2 депрецирует тип, на который ссылаются задачи | `deprecated` влияет только на резолв «последняя активная»; задача продолжает менять статус | `test_deprecated_version_stops_resolving_but_keeps_its_tasks_alive` |
| T15 | Эскалация «заведение задач → настройка процесса» | A1 создаёт свой тип | `task_types.manage` — отдельное право, не покрываемое `tasks.write` | `test_task_types_require_their_own_permission` |
| T16 | Рассогласование пары ключ/категория | A1 присылает `systemStatusCategory` в теле | поле не объявлено ни в одной request-схеме; категория всегда вычисляется из lifecycle | `test_client_cannot_set_the_category` |

## 4. Failure model

| Сценарий | Поведение |
|---|---|
| Тип задачи не найден при чтении (рассогласование БД) | `500` не маскируется: FK `NOT NULL` делает состояние недостижимым, тест на инвариант в миграции |
| Ребро `claimStatus` не объявлено из текущего статуса | claim **проходит**, статус не меняется (SPEC §4.4) |
| Ребро в `completionStatus` не объявлено | `:complete` отказывает `422 invalid_transition`; задача не завершена, claim не снят |
| Переход в текущий статус | `422 invalid_transition` — единственное сужение контракта |
| Неизвестный ключ в `?status=` | пустая страница, не `422`: глобального словаря ключей больше нет |
| Неизвестная категория в `?systemStatusCategory=` | `422 invalid_status_category` — словарь категорий как раз глобален |
| Гонка аллокации версии типа | advisory-лок на `(tenant, key)`; уникальный индекс — страховка |
| Downgrade миграции | пользовательские ключи статусов приводятся к легаси по категории; потеря необратима и задокументирована |
| Задача с типом, у которого нет активных версий | существующая задача работает; новая задача с этим `typeKey` — `404` |

## 5. Осознанно не закрыто

- **Категория `blocked` не запрещает claim.** Сегодняшнее поведение сохранено
  дословно (SPEC §6.1). Запрет — продуктовое решение с собственной миграцией
  ожиданий; вводить его молча вместе с рефакторингом было бы худшим моментом.
- **Ретайп задачи отсутствует.** Ошибочно выбранный тип исправляется только на
  уровне БД. Отображение статусов старого lifecycle в новый — отдельное
  решение (SPEC §5.2).
- **`field_schema` не применяется.** Колонка заводится пустой; валидация полей
  задачи появляется в WI-3. До тех пор схема — задекларированное намерение, а
  не действующий контроль.
- **Тенант может объявить бессмысленный, но валидный процесс** (например,
  граф без пути к успешному финалу из части статусов). Проверка достижимости
  не вводится: она превращает конфигурацию в решаемую задачу на графах и
  запрещает промежуточные состояния, которые тенант заполняет постепенно.
- **Смысл ключа статуса не проверяется.** Ключ `done` категории `active`
  допустим и будет вести себя как активный. Это прямое следствие решения ADR-
  0015 «core не принимает решений по ключу»; лечится наблюдаемостью
  (категория выводится в API и в событиях), а не запретом.
